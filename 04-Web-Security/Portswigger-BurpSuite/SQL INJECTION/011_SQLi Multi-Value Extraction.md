On 27 October 2026, I completed the PortSwigger Web Security Academy lab **“SQL injection UNION attack, retrieving multiple values in a single column.”** The lab demonstrated how a SQL injection vulnerability in a product category filter could be used to retrieve information from a separate database table.

The goal was to retrieve usernames and passwords from a table named `users`, identify the administrator's credentials, and log in as the `administrator` user.

The important challenge was that the application's query returned two columns, but only one of them could display text. I therefore needed to find a compatible result structure and combine the username and password into one string.

## 4. Understanding the Vulnerability

### What is SQL injection?

SQL injection occurs when an application places untrusted input into a SQL query in a way that allows the input to change the query's intended structure. Depending on the application's database permissions and implementation, an attacker may be able to retrieve or modify data that the feature was not intended to expose.

In this lab, the vulnerable input was the product category filter. The feature was intended to show products belonging to a selected category, but the input could be manipulated to affect the SQL query.

A simplified illustration of the intended query is:

```sql
SELECT name, description
FROM products
WHERE category = 'Gifts';
```

This is an illustrative example of the likely query structure, not a verified copy of the lab's internal source code.

The intended behavior is to return product names and descriptions for the selected category. The vulnerability allowed an injected query to append another result set and display records from a different table.

### Why is this significant?

The category filter is an ordinary application feature. However, when user input is treated as SQL syntax instead of only as data, the database may process instructions that the application developer did not intend. This lab showed how a product-filtering feature could expose account credentials.

## 5. Step-by-Step Methodology

### Step 1 — Find the category-filter request

**What I did:** I opened the lab, selected a product category, and inspected the resulting request in Burp Suite's HTTP history. I identified the `category` parameter and sent the request to Repeater.

A request had a structure similar to:

```http
GET /filter?category=Gifts HTTP/2
```

The exact request may contain additional headers and can vary by session.

**Why I did it:** Before testing an application, I needed to locate the input that controls the behavior I wanted to examine. The category parameter was a suitable candidate because its value was sent to the server and influenced which products were displayed.

**How I used it:** In Repeater, I changed the category value while keeping the rest of the request substantially the same.

**What it gave me:** A repeatable way to test the parameter and compare the response. This alone did not prove SQL injection; it established the point where I would perform further tests.

### Step 2 — Determine the query's column structure and identify a text column

**Payload used:**

```sql
'+UNION+SELECT+NULL,'abc'--
```

**Why I used this payload:** A `UNION` query must return the same number of columns as the original query, and the corresponding columns must have compatible data types. If the injected query has the wrong number of columns, the database generally rejects it. If the data types are incompatible, the database may also return an error.

I used `NULL` for the first column because it can be compatible with many SQL data types. I used `'abc'` in the second column because it is a simple text value that should be easy to recognize in the response if that column is displayed.

**How the payload works:**

- **`'` — closing the original string:** The quote attempts to end the string literal around the original category value. Whether this works depends on the application's actual query construction.
- **`UNION SELECT` — appending another result set:** `UNION` combines rows from the original query with rows from the injected `SELECT`, provided the column structures are compatible.
- **`NULL` — filling the first column:** This supplies a value for the first column without requiring a specific concrete value.
- **`'abc'` — testing text output:** This provides a recognizable string in the second column.
- **`--` — commenting out the remainder:** In SQL dialects that support this comment syntax, it can prevent the rest of the original statement from interfering with the injected query. Comment syntax and whitespace requirements depend on the database and query context.
- **`+` characters in the parameter:** In a URL query parameter, `+` is commonly decoded as a space. Thus, the URL-encoded payload is interpreted by the application as SQL text containing spaces.

**What it gave me:** The test worked and established that the query returned two columns, with the second column able to display text. This was the key information needed to build the data-retrieval query.

### Step 3 — Retrieve values from the `users` table

**Payload used:**

```sql
'+UNION+SELECT+NULL,username||'~'||password+FROM+users--
```

**Why I used this payload:** The lab specified that the database contained a table named `users` with `username` and `password` columns. I wanted to retrieve both fields. Because only one output column was suitable for displaying text, I needed to combine the two values into a single string.

**How the payload works:**

- **`'`** attempts to close the original category string.
- **`UNION SELECT`** appends the results of another query to the original result set.
- **`NULL`** fills the first column to match the original query's two-column structure.
- **`username`** selects the username value from each row in `users`.
- **`||`** is a string-concatenation operator in SQL dialects such as PostgreSQL and SQLite.
- **`'~'`** inserts a tilde between the two fields. The separator makes it easier to tell where the username ends and the password begins.
- **`password`** selects the password value from each row.
- **`FROM users`** identifies the table from which the values are retrieved.
- **`--`** comments out the remaining portion of the original statement in this query context.

The expression:

```sql
username || '~' || password
```

combines three parts: the username, a tilde, and the password. If a row contained `administrator` as its username and `example` as its password, the resulting string would look like:

```text
administrator~example
```

The word `example` here is only an illustration, not the lab password.

**What it gave me:** The application response displayed each username and password together in the same result column. This confirmed that the injected query had retrieved data from the `users` table.

### Step 4 — Examine the server response

The response from Burp Suite Repeater included:

```http
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
```

The HTML body showed the injected query expression in the page heading and displayed the following rows:

```text
wiener~u07lu33ak83147uvuuvt
administrator~mpmafymtvdhj6dm9vt3v
carlos~ow066x1lfv2l5ovm2z7a
```

**Why I examined the response:** A request being accepted or returning HTTP `200 OK` does not, by itself, prove that a SQL injection worked. I needed to inspect the actual content to see whether the expected injected result appeared.

**What I looked for:** I looked for the recognizable output and the credential pairs, especially the row beginning with `administrator~`.

**What it gave me:** The response provided direct evidence that the injected query returned data from the `users` table. The tilde made it possible to separate each username from its associated password.

**Evidence handling:** The values above are credentials from the intentionally vulnerable training lab. They must not be reused as credentials for any real account. When documenting real assessments, sensitive values should be redacted and evidence should be handled according to the engagement's rules.

### Step 5 — Log in as administrator

**What I did:** I returned to the lab's login page, entered `administrator` as the username, and entered the corresponding password obtained from the response. I submitted the form.

**Why I did it:** The lab objective required more than retrieving the values; it required using the administrator's credentials to authenticate successfully.

**What it gave me:** The lab status changed to **Solved**. This confirmed that the credentials retrieved through the injection were valid for the administrator account in the lab.

## 6. Why the Attack Worked

### Column count matching

The original query returned two columns. The injected query also returned two:

```sql
SELECT NULL, username || '~' || password
FROM users
```

The first column supplied `NULL`; the second supplied a concatenated text value. Matching the result structure was necessary for the `UNION` operation to succeed.

### Data type compatibility

The output column that displayed the injected data needed to accept text. The test string `'abc'` helped establish that the second column could display text in the response.

### String concatenation

The application displayed only one suitable text column. Concatenation made it possible to return both fields through that single column, instead of needing two separate displayed columns.

### Untrusted input changed SQL structure

The root cause was unsafe handling of the category input. The input was interpreted in a way that allowed SQL syntax to be introduced into the query. The database then executed the additional `SELECT` and returned records from `users`.

## 7. Findings and Impact

**Finding:** UNION-based SQL injection in the product category filter.

**Evidence:** The test payload returned a recognizable text value, and the extraction payload returned username-password pairs from the `users` table.

**Demonstrated impact in the lab:**

- **Confidentiality:** Account-related data was exposed through a page intended to display product results.
- **Authentication:** The retrieved administrator credentials enabled a successful login.
- **Potential privilege impact:** Access to an administrator account could permit privileged actions, depending on the application's authorization model.

The impact of a SQL injection vulnerability in a real system depends on the database account's permissions, the application's access controls, the affected data, and the privileges of any compromised account. The lab demonstrates one possible impact; it does not mean every SQL injection vulnerability provides the same level of access.

## 8. How a Tester Might Recognize Similar Issues

This lab helped me learn a structured approach for investigating suspected SQL injection:

1. **Map the inputs:** Identify URL parameters, form fields, cookies, and API values that may influence database operations.
2. **Record a baseline:** Capture a normal request and note the response status, body, and other observable behavior.
3. **Change one variable:** Modify one input at a time in an authorized environment.
4. **Compare the results:** Look for repeatable changes that suggest the input affected database query logic.
5. **Validate the hypothesis:** Do not treat a parameter, an HTTP error, or a changed page as proof on its own. Confirm that the behavior is consistent with SQL injection.
6. **Record evidence:** Preserve the relevant requests and responses, redact sensitive data where appropriate, and clearly distinguish observations from assumptions.

A category filter is not inherently vulnerable just because it appears in a URL. Similarly, a site displaying different products for different valid categories is normal behavior. The important clue is evidence that user-controlled input is being interpreted as part of the SQL statement.

## 9. Remediation

The primary defence is to use **parameterized queries (prepared statements)**. Parameterization keeps SQL instructions separate from user-supplied values, so an input containing SQL-looking characters is treated as data rather than executable SQL syntax.

Other defensive measures include:

- Avoid constructing SQL statements by concatenating untrusted input.
- Validate inputs according to the expected format and allowed values; validation complements but does not replace parameterization.
- Apply least privilege to database accounts so the application can access only the data it requires.
- Avoid returning detailed database errors or sensitive query results to end users.
- Store passwords using an appropriate salted password-hashing scheme rather than plaintext.
- Add security tests for database access paths and review query construction during code changes.

## 10. Lessons Learned

By completing this lab, I learned that:

- SQL injection can allow input to alter the structure of a database query.
- A `UNION` attack requires compatible column counts and data types.
- `NULL` and a recognizable text value can help identify a compatible output column in an authorized test.
- String concatenation can return multiple database fields through a single output column.
- A feature that appears unrelated to account data, such as a product filter, may expose sensitive records if its SQL query is constructed unsafely.
- HTTP status codes must be interpreted alongside the response body and the test objective.
- A finding should be supported by reproducible evidence and its impact should be described accurately.
- Parameterized queries are the primary defence against SQL injection.
