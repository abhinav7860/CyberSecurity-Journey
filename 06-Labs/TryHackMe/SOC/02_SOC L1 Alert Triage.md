# Task 2 — Events and Alerts

## What is an Event?

An **event** is something that happens in a system.

Examples include:

- A user logging in
- A process launching
- A file being downloaded
- A user accessing a resource
- A network connection being made

The event itself is not necessarily malicious. Most events happening in an environment are normal and expected.

The important part is that systems need to record these events so that security teams can investigate activity later.

---

## From Events to Alerts

The general process I learned is:

```text
Event occurs
     ↓
Operating System / Firewall / Cloud Provider logs the event
     ↓
Logs are shipped to SIEM / EDR
     ↓
Detection rule analyses the events
     ↓
Suspicious activity matches the rule
     ↓
Alert is generated
     ↓
SOC analyst investigates the alert
```

For example:

1. A user downloads a file.
2. The operating system or security product records the download.
3. The log is sent to a security solution such as a SIEM.
4. A detection rule checks the activity.
5. If the activity matches suspicious behaviour, an alert is generated.
6. The SOC analyst reviews the alert and decides what it means.

---

## What is an Alert?

An **alert** is a notification generated by a security solution when a specific event or sequence of events occurs that matches a detection rule.

This is important because a SOC can receive **millions of logs per day from thousands of systems**.

Most of those events are expected and do not require immediate human attention.

It would not be practical for an analyst to manually inspect every single log.

Alerts solve this problem by highlighting events or sequences of events that deserve attention.

Instead of manually reviewing millions of raw logs, SOC analysts can focus on a much smaller number of alerts.

### Important distinction

```text
Event = Something happened.

Log = The system recorded that something happened.

Alert = A security system decided that the event/activity deserves attention.
```

An alert does **not automatically mean that an attack has happened**.

It still needs to be investigated.

# SOC L1 Role in Alert Triage

SOC L1 analysts are the **first line of defence**.

They are usually the analysts who work with alerts the most.

Depending on the organisation, an L1 analyst may receive anywhere from zero to around a hundred alerts a day.

Every alert has the possibility of revealing a cyberattack, so the analyst has to make decisions carefully.

Different members of a SOC have different responsibilities.

### SOC L1 Analysts

My understanding of the L1 role is:

- Review alerts.
- Distinguish suspicious activity from legitimate activity.
- Investigate the available information.
- Decide whether an alert is likely to be a real threat or harmless activity.
- Escalate the alert to L2 when deeper investigation or remediation is required.

### SOC L2 Analysts

L2 analysts receive alerts escalated by L1 analysts.

They perform:

- Deeper analysis
- More detailed investigation
- Incident response
- Remediation when required

### SOC Engineers

SOC engineers make sure that detection rules and alerts contain enough useful information for analysts to investigate efficiently.

### SOC Manager

The SOC manager tracks the speed and quality of alert triage and makes sure important attacks are not missed.

# Task 3 — Alert Properties

After understanding how alerts are generated, the next thing I learned was how to read the information contained inside an alert.

Alert properties can vary depending on the SIEM or security solution, but there are several common fields that SOC analysts should understand.

---

## 1. Alert Time

The **Alert Time** shows when the alert was created.

The alert may be generated a few minutes after the actual event happened.

For example:

```text
Event Time: March 21, 15:32
Alert Time: March 21, 15:35
```

This means the suspicious activity happened at 15:32, but the detection system generated the alert at 15:35.

### Why this matters

When investigating an alert, I should not assume that the alert timestamp is exactly when the suspicious activity occurred.

I may need to look at the surrounding events around the actual event time.

---

## 2. Alert Name

The **Alert Name** gives a short summary of what the detection rule identified.

Examples:

- Unusual Login Location
- Email Marked as Phishing
- Windows RDP Bruteforce
- Potential Data Exfiltration

The alert name is useful for quickly understanding what type of activity triggered the detection.

---

## 3. Alert Severity

**Alert Severity** describes how urgent or serious the alert is.

The initial severity is generally set by detection engineers, although analysts may be able to change it if the investigation shows that the original severity was inappropriate.

Common severity levels are:

```text
Low / Informational
        ↓
Medium / Moderate
        ↓
High / Severe
        ↓
Critical / Urgent
```

The severity helps the SOC decide which alerts should receive attention first.

However, severity is not the same thing as the final verdict.

A high-severity alert can still turn out to be a false positive.

---

## 4. Alert Status

The **Alert Status** tells me what stage the alert is currently in.

Examples:

- **New / Unassigned** — Nobody has taken ownership yet.
- **In Progress / Pending** — An analyst is currently investigating it.
- **Closed / Resolved** — The investigation has been completed.

There can also be additional custom statuses depending on the organisation.

---

## 5. Alert Verdict

The **Alert Verdict** or classification tells me whether the alert turned out to represent a real threat or harmless activity.

The two important classifications are:

### True Positive

A **True Positive (TP)** means the alert correctly detected malicious or unwanted activity.

```text
Detection triggered
        ↓
Activity is actually malicious
        ↓
TRUE POSITIVE
```

### False Positive

A **False Positive (FP)** means the alert was triggered, but the activity was legitimate or did not represent a security threat.

```text
Detection triggered
        ↓
Activity is legitimate / not malicious
        ↓
FALSE POSITIVE
```

This distinction is very important in SOC work because analysts need to separate genuine threats from normal activity.

---

## 6. Alert Assignee

The **Alert Assignee** shows which analyst is responsible for investigating the alert.

The assignee can also be called the **alert owner**.

Assigning an alert to myself means that I am taking responsibility for investigating it.

This also helps prevent multiple analysts from unknowingly working on the same alert.

---

## 7. Alert Description

The **Alert Description** explains what the alert is about.

It generally contains information such as:

- The logic of the rule that generated the alert
- Why the activity may indicate an attack
- Sometimes instructions on how the alert should be investigated

The description gives the analyst initial context before starting the investigation.

---

## 8. Alert Fields

**Alert Fields** contain the actual values and indicators associated with the alert.

Depending on the alert, these can include:

- Affected hostname
- Username
- IP address
- Entered command line
- Target file
- File hash
- URL
- Other relevant indicators

These fields are often extremely important during investigation because they tell me **what actually happened, where it happened, and who or what was involved**.

# Example Alert From the Dashboard

One alert I inspected was:

**Double-Extension File Creation**

The alert showed information such as:

```text
Host:
LPT-HR-009

Process Name:
chrome.exe

Process User:
S.Conway

Target File:
C:\Users\S.Conway\Downloads\cats2025.mp4.exe

File MotW:
https://freecatvideoshd.monster/cats2025.mp4.exe

File MD5:
14d8486f3f63875ef93cfd240c5dc10b
```

### Why the target file is suspicious

The file is named:

```text
cats2025.mp4.exe
```

At first glance, a user might think it is a video because of the `.mp4` extension.

However, the **actual executable extension is `.exe`**.

This is an example of a **double-extension file**, which can be used to trick users into opening malicious executables.

The alert description explained that this detection looks for files such as:

```text
*.pdf.exe
*.gif.lnk
```

because attackers may use filenames like these in phishing attacks to make a malicious executable look like a harmless document, image, or video.

The presence of this type of filename does not by itself prove that the file is malicious, but it is suspicious enough to investigate.

# Task 4 — Alert Prioritisation

After learning how to read an alert, I needed to understand **which alert to investigate first**.

A SOC can have many alerts waiting in a queue, so an analyst cannot necessarily investigate them in random order.

The process of deciding which alert should be handled first is called **Alert Prioritisation**.

The goal is to make sure that potentially serious threats are investigated in time.

---

## Generic Alert Prioritisation Process

The room explains a simple and commonly used prioritisation method.

### Step 1 — Filter the alerts

First, I should make sure that I am not taking an alert that:

- Has already been reviewed
- Is already being investigated by another analyst
- Has already been resolved

I should focus on alerts that are:

- New
- Unseen
- Unresolved

This avoids duplicate work and prevents me from interfering with another analyst's investigation.

---

### Step 2 — Sort by Severity

After filtering, I should generally prioritise:

```text
Critical
   ↓
High
   ↓
Medium
   ↓
Low
```

The reason is that detection engineers design rules so that critical alerts are generally more likely to represent serious threats and have a greater potential impact.

Therefore, higher-severity alerts normally receive attention before lower-severity alerts.

---

### Step 3 — Sort by Time

If multiple alerts have the same priority/severity level, the room recommends starting with the **oldest** alerts and then moving toward the newest ones.

The reasoning is that an older unresolved breach may have been active for longer.

For example:

```text
Older suspicious activity
        ↓
Attacker has had more time
        ↓
Potentially more damage / data exposure
```

A newer alert may represent an attack that has only recently started.

Therefore, when using this simple prioritisation method, I should not automatically pick the newest alert first.

# Task 5 — Alert Triage

Once I know which alert to handle, the actual investigation begins.

The process of reviewing and analysing an alert is called **Alert Triage**.

The room also mentions that the same general process can be called:

- Alert review
- Alert handling
- Alert processing
- Alert investigation
- Alert analysis

In this room, the term **Alert Triage** is used.

The exact workflow can vary slightly between SOC teams, but the basic process remains similar.

# Alert Triage Workflow

The workflow shown in the room can be summarised as:

```text
START
  ↓
Prioritise the alerts and select one
  ↓
Assign the alert to yourself
  ↓
Move the alert to "In Progress"
  ↓
Read the alert's name and description
  ↓

  ↓

  │             ↓

  │

                ↓
          Make your final verdict
                ↓

             ├── YES → Escalate to L2
             │
             └── NO → Add your alert comment
                           ↓
                    Move alert to "Closed"
```

# Initial Actions

The initial actions are important because they establish ownership and make sure I do not interfere with another analyst's investigation.

The initial steps are:

### 1. Assign the alert to myself

This means I am taking ownership of the alert.

### 2. Change the status to "In Progress"

This tells the SOC that the alert is currently being investigated.

### 3. Familiarise myself with the alert

Before making conclusions, I should read:

- Alert name
- Alert description
- Alert fields
- Important indicators

This gives me the initial context needed for the investigation.

---

# Investigation

The investigation is usually the most technically demanding part of alert triage.

The goal is to understand whether the activity is legitimate or malicious.

I need to use the information in the alert and examine relevant activity in the SIEM or EDR.

---

## Workbooks

Some SOC teams provide **Workbooks** for specific alert categories.

A workbook can also be referred to as a:

- Playbook
- Runbook

A workbook provides step-by-step instructions for investigating a particular type of alert.

For example, a phishing alert may have a workbook explaining:

```text
1. Identify the affected user.
2. Check the email sender.
3. Inspect the URL.
4. Check the attachment.
5. Search for related events.
6. Determine whether the email is malicious.
7. Escalate if necessary.
```

Using a workbook helps L1 analysts perform investigations consistently instead of relying entirely on memory.

---

# If No Workbook Is Available

If there is no workbook, the room recommends several important investigation steps.

## 1. Understand who or what is under threat

Identify the affected entity.

This could be:

- User
- Hostname
- Cloud environment
- Network
- Website
- Other affected system

For example:

```text
Affected User → S.Conway
Host → LPT-HR-009
```

Understanding the affected entity helps establish the scope of the alert.

---

## 2. Understand the Action

I need to understand what activity caused the alert.

Examples include:

- Suspicious login
- Malware execution
- Phishing
- Data exfiltration
- Brute-force attack
- Suspicious file creation

The alert name and description are useful starting points.

---

## 3. Review Surrounding Events

I should not look only at the event that triggered the alert.

I should also look at events occurring:

- Shortly before the alert
- Shortly after the alert

This can reveal additional activity.

For example:

```text
Suspicious login
      ↓
New process launched
      ↓
PowerShell executed
      ↓
Credential access
      ↓
Data transfer
```

A single event might look harmless, but the sequence of events can reveal a much more suspicious attack chain.

This is one of the important things I learned from the triage process: **context matters**.

---

## 4. Use Threat Intelligence

If necessary, I can use threat intelligence platforms or other available resources to verify my findings.

For example, I may investigate:

- IP addresses
- Domains
- URLs
- File hashes
- Malware indicators

The goal is to determine whether an indicator is associated with known malicious activity.

---

# Final Actions

After completing the investigation, I need to make a final decision.

The two main verdicts are:

```text
TRUE POSITIVE
      OR
FALSE POSITIVE
```

### True Positive

The alert represents real malicious or unwanted activity.

### False Positive

The alert was triggered, but the activity is legitimate or does not represent a real security threat.

---

# Escalation

If the investigation indicates that the alert requires deeper analysis or remediation, I may need to **escalate it to an L2 analyst**.

The general idea is:

```text
L1 Investigation
      ↓
Needs deeper investigation?
      ↓
    YES
      ↓
Escalate to L2
```

If escalation is not required, I can continue with the final actions.

---

# Alert Comment

Before closing an alert, I should add a detailed comment explaining what I investigated and why I reached my verdict.

A good alert comment should contain enough information for another analyst to understand my reasoning without having to repeat the entire investigation.

For example:

```text
Reviewed the affected user and host activity.
Checked the events surrounding the alert and found no additional
suspicious activity. The observed behaviour appears legitimate.
Verdict: False Positive.
```

The exact comment depends on what I actually discover during the investigation.

---

# Closing the Alert

After the investigation is complete and the necessary comments/escalation have been handled, the alert can be moved to:

**Closed**

The basic lifecycle can therefore look like:

```text
New
 ↓
Assigned
 ↓
In Progress
 ↓
Investigated
 ↓
Verdict
 ↓
Comment / Escalation
 ↓
Closed
```

# Important Concepts I Learned Today

## Event vs Alert

An event is something that happens.

An alert is a notification generated when a security system detects activity that matches a particular detection condition.

```text
Event → Logged → Analysed by detection rule → Alert
```

---

## Severity vs Verdict

These are not the same thing.

**Severity** tells me how urgent/serious the alert is expected to be.

**Verdict** tells me what I concluded after investigation.

For example:

```text
Severity: High
Verdict: False Positive
```

This is possible.

A high-severity alert does not automatically mean that it is a real attack.

---

## Status vs Verdict

Status tells me **where the alert is in the workflow**.

Verdict tells me **what the investigation concluded**.

Example:

```text
Status: In Progress
Verdict: None
```

This means the alert is currently being investigated and no final conclusion has been made yet.

After investigation:

```text
Status: Closed
Verdict: True Positive
```

This means the investigation is complete and the activity was confirmed as a real threat.

# My Takeaway

Today I understood that **alert triage is not simply opening an alert and deciding whether it is malicious**.

There is a proper workflow.

First I need to prioritise the alert, take ownership of it, move it to In Progress, understand the alert details, investigate the activity and surrounding events, use a workbook or other investigation resources when available, and finally make a verdict.

If it is a real threat and needs deeper investigation, it should be escalated to L2. If no escalation is needed, I should document my reasoning and close the alert.

The biggest thing I learned is that **an alert is only a starting point for an investigation**. A True Positive or False Positive verdict should come from analysing the available evidence, not simply from the alert name or severity.
