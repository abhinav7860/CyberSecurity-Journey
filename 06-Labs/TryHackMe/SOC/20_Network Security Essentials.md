# Task 1 --- Introduction

Networks are the backbone of modern organizations. Workstations,
servers, applications, security devices and other systems are connected
together.

The **network perimeter** is the boundary between the internal
organization and the external Internet.

From a SOC perspective, monitoring the perimeter can help detect:

-   Port scanning
-   Brute-force attempts
-   Exploitation attempts
-   Suspicious external connections
-   Data exfiltration

# Task 3 --- A Network: Overview

A network is an organized collection of connected devices that
communicate with each other and share resources.

## 1. User Workstations / Endpoints

These are the PCs and laptops used by employees.

They are common targets because attackers can use phishing emails or
malicious downloads to compromise an employee's machine.

**Security importance:** Endpoint logs can show malicious processes,
while network logs may reveal the first **C2 (Command and Control)**
connection.

## 2. File & Database Servers

**File servers** provide centralized access to shared documents.

**Database servers** store structured information such as customer, HR
and financial data.

**Security importance:** These systems contain valuable data, so
attackers often target them. Ransomware may target file servers, while
attackers may steal database information and exfiltrate it.

## 3. Application Servers

Examples include:

-   Web servers
-   Email servers
-   VPN gateways

Because some of these services are externally accessible, they are
frequently targeted.

As a SOC analyst, I would monitor:

-   Application logs
-   Firewall alerts
-   IDS/IPS alerts
-   External IP connections
-   Brute-force attempts
-   Exploitation attempts

## 4. Active Directory / Authentication Servers

**Active Directory (AD)** manages users, computers, groups and access
permissions in many enterprise networks.

It is extremely important because compromised AD accounts can provide
attackers with access to multiple systems.

I would monitor:

-   Multiple failed login attempts
-   Password spraying
-   Unusual login times
-   Suspicious external logins
-   Accounts accessing systems they normally do not use

## 5. Routers & Switches

A **router** connects different networks, commonly connecting the
internal network to the Internet.

A **switch** connects devices within the same network.

If compromised, network infrastructure could potentially be used to:

-   Intercept traffic
-   Manipulate traffic
-   Redirect traffic
-   Create hidden communication paths

## 6. Firewalls / Perimeter Devices

A firewall controls traffic between trusted and untrusted networks. It
checks traffic against security rules and decides whether traffic should
be **allowed or blocked**.

Modern firewalls can also provide:

-   Deep packet/application inspection
-   Intrusion prevention
-   Malware detection

**Security importance:** Firewall logs are useful for identifying port
scans, brute-force attempts, exploitation attempts and suspicious
outbound connections.

# Task 4 --- Network Visibility

## What is Network Visibility?

Network visibility means being able to monitor and understand what is
happening across a network.

A simple idea I learned here:

> **You can't defend what you can't see.**

Good visibility helps security analysts:

-   Detect anomalies
-   Investigate incidents
-   Hunt for threats
-   Build attack timelines
-   Identify affected systems
-   Meet monitoring/compliance requirements

Network visibility mainly comes from two categories:

1.  **Host-centric logs**
2.  **Network-centric logs**

------------------------------------------------------------------------

# Host-Centric Logs

Host-centric logs are generated by individual systems such as Windows
machines, Linux servers, macOS systems, workstations and servers.

They provide a detailed view of what happened **inside a specific
machine**.

## Main Sources

### Operating System Logs

Examples:

-   Windows Event Logs
-   Linux `syslog`
-   macOS logs

They can contain:

-   User logins
-   Failed logins
-   Process creation
-   Service starts
-   System events

### Application Logs

Applications can generate their own logs.

Examples:

-   Apache
-   Nginx
-   MySQL
-   MSSQL

### Security Tool Logs

Examples:

-   Antivirus
-   EDR
-   HIDS

## Why Host Logs Matter

Host logs can help answer:

**What exactly happened on the compromised machine?**

They can identify:

-   Files accessed or deleted
-   Malicious processes
-   PowerShell/script execution
-   Service changes
-   Registry modifications
-   User activity
-   Malware execution

------------------------------------------------------------------------

# Network-Centric Logs

Network-centric logs show what happens **between systems**.

Typical information includes:

-   Source IP
-   Destination IP
-   Source port
-   Destination port
-   Protocol
-   Allowed/blocked action
-   Connection information

They help answer:

-   Who communicated with whom?
-   When did it happen?
-   Which service/port was involved?
-   Was the connection allowed or blocked?

## Main Network-Centric Sources

### Firewalls

Firewall logs record allowed and denied network connections and are
often one of the first places to check for suspicious Internet traffic.

### IDS/IPS

**IDS (Intrusion Detection System)** and **IPS (Intrusion Prevention
System)** monitor traffic for known malicious signatures, suspicious
patterns and anomalous behaviour.

### Routers & Switches

These can provide **flow data**, which summarizes network conversations
and can show who communicated, for how long and how much data was
transferred.

### Web Proxies

Proxy logs can show which websites users accessed and help investigate
malicious websites, policy violations and possible data exfiltration.

### VPN

VPN logs show remote access activity, including who connected, where
they connected from and when they connected.

------------------------------------------------------------------------

# Host Logs vs Network Logs

  Host-Centric                    Network-Centric
  ------------------------------- -------------------------------------
  Shows activity on a device      Shows communication between devices
  Detailed system information     Broader traffic information
  Processes and files             IPs, ports and protocols
  User activity                   Network connections
  Registry/service changes        Allowed/blocked traffic
  Useful for detailed forensics   Useful for network-wide visibility

### Easy way to remember

**Host logs = what happened inside the room.**

**Network logs = who entered and left the building.**

For a proper investigation, both should be correlated.

------------------------------------------------------------------------

# What Network-Centric Logs Can Help Detect

### Early Threat Detection

-   Port scans
-   Brute-force attempts
-   Connections from malicious IPs

### Command & Control (C2)

Communication between a compromised internal machine and an
attacker-controlled server.

### Lateral Movement

An attacker moving between internal systems.

### Data Exfiltration

Large or unusual outbound transfers that may indicate stolen data being
sent outside the organization.

### Attack Scope

Identifying other systems that a compromised machine communicated with.

# Task 5 --- Network Perimeter

## What is a Network Perimeter?

The network perimeter is the boundary between an organization's
**internal/trusted network** and the **external/untrusted Internet**.

I think of it as the **front door of an organization**.

### Internal network

Contains systems such as:

-   Employee workstations
-   Internal servers
-   Databases
-   Active Directory
-   Business applications

### External network

The Internet, where the organization can be exposed to potential
attackers.

------------------------------------------------------------------------

# Main Components of a Network Perimeter

## Firewall

Acts as a gatekeeper and filters traffic between networks.

## Router / Gateway

Routes traffic between different networks and can enforce access rules.

## DMZ

A **Demilitarized Zone (DMZ)** is a separate network segment used for
public-facing services such as web, mail or VPN services.

The goal is to keep public-facing systems separated from the most
sensitive internal systems.

## VPN Gateway

Provides controlled remote access for employees connecting from outside
the organization.

------------------------------------------------------------------------

# Example Small Enterprise Network

A simple design can be visualized as:

``` text
                    INTERNET
                        |
                 [ Firewall ]
                   /                         /                         DMZ       Internal LAN
                 |             |
           [Web Server]    [Workstations]
                               |
                 +-------------+-------------+
                 |             |             |
              [AD]        [File Server] [Database]
```

Remote access could look like:

``` text
Remote User
     |
    VPN
     |
VPN Gateway / Firewall
     |
Internal Network
```

The important idea is that public-facing services should not
automatically have unrestricted access to sensitive internal systems.

------------------------------------------------------------------------

# Why the Network Perimeter Matters

Attackers commonly begin from outside the organization.

A typical attack path can be:

1.  Scan public IP addresses.
2.  Find open ports.
3.  Identify exposed services.
4.  Search for vulnerabilities.
5.  Attempt brute-force attacks.
6.  Exploit weak or outdated services.
7.  Establish access.
8.  Attempt lateral movement or data theft.

Common exposed services that can become attack targets include:

-   RDP
-   SSH
-   SMB
-   MySQL

A weak or misconfigured perimeter can lead to:

-   Unauthorized access
-   Malware infection
-   Data breaches
-   Further compromise of internal systems

------------------------------------------------------------------------

# What I Would Monitor as a SOC Analyst

## Firewall logs

Look for:

-   Repeated blocked connections
-   Repeated attempts against the same port
-   Suspicious source IPs
-   Unexpected outbound traffic

## IDS/IPS alerts

Look for:

-   Known attack signatures
-   Exploit attempts
-   Suspicious traffic patterns

## VPN logs

Look for:

-   Unusual login locations
-   Repeated failed logins
-   Unexpected login times
-   Suspicious accounts

## Outbound traffic

Look for:

-   Unknown external destinations
-   Large data transfers
-   Repeated connections to the same suspicious IP/domain
-   Possible C2 beaconing

# Scenario 1 --- Port Scanning

A port scan happens when an attacker probes multiple ports to find
available services.

Example:

``` text
203.0.113.10 → 10.0.0.20:21
203.0.113.10 → 10.0.0.20:22
203.0.113.10 → 10.0.0.20:23
203.0.113.10 → 10.0.0.20:25
203.0.113.10 → 10.0.0.20:53
```

The important pattern is:

> **One source IP repeatedly contacting different ports on a target.**

This is a strong indicator of reconnaissance/port scanning.

### Analyst verdict

The attacker is trying to discover an exposed service that can
potentially be targeted.

------------------------------------------------------------------------

# Scenario 2 --- Web Attacks

WAF logs can provide more context than a simple firewall block.

Examples of attacks shown in the logs included:

-   XSS
-   SQL Injection
-   Directory Traversal

Useful filtering idea:

``` text
action=BLOCK
```

This lets me quickly focus on requests that the WAF identified and
blocked.

### Analyst verdict

Multiple blocked web attack types from the same suspicious source
indicate that the attacker is actively targeting the web application.

------------------------------------------------------------------------

# Scenario 3 --- VPN Brute Force

VPN authentication logs can become noisy when an attacker repeatedly
guesses usernames and passwords.

The important pattern is:

``` text
FAILED_AUTH
FAILED_AUTH
FAILED_AUTH
FAILED_AUTH
...
SUCCESS_AUTH
```

A large number of failures from one source IP is suspicious.

### Analyst verdict

The attacker is attempting to discover valid credentials and gain remote
access to the internal network.

------------------------------------------------------------------------

# Key Detection Patterns

I noted these patterns from the task:

  Pattern                              Possible Activity
  ------------------------------------ -----------------------------
  One source → many ports              Port scanning
  Many failed logins from one source   Brute force
  Regular repeated connections         Malware beaconing
  Large outbound transfers             Data exfiltration
  IDS alert with attack type           Higher-confidence detection

The important point is that **context matters**. A firewall may only
tell me that traffic was blocked, while an IDS/WAF can provide
additional information about why the traffic is suspicious.

# Method 1 --- Manual Log Analysis

I first inspected the logs from the command line.

## Checking Firewall Logs

``` bash
head firewall.log
```

This gives a quick look at the structure of the firewall logs.

I then focused on blocked traffic:

``` bash
cat firewall.log | grep "BLOCK" | head
```

The blocked connections showed external systems probing internal hosts
using ports such as:

``` text
21
22
23
445
3389
```

These ports correspond to services such as FTP, SSH, Telnet, SMB and
RDP.

------------------------------------------------------------------------

# Finding the IP Performing the Most Reconnaissance

To identify the source IP with the highest number of blocked requests, I
used:

``` bash
cat firewall.log | grep "BLOCK" | cut -d' ' -f5 | cut -d: -f1 | sort -nr | uniq -c
```

The result showed one IP with the highest number of blocked requests.

### Answer

``` text
203.0.113.45
```

This was the external IP I used as the main pivot for the rest of the
investigation.

------------------------------------------------------------------------

# Checking Whether the Attacker Got Through

After identifying the suspicious IP, I checked whether any traffic from
it was allowed:

``` bash
cat firewall.log | grep 203.0.113.45 | grep "ALLOW"
```

The output showed allowed connections to internal services including:

``` text
445
22
3389
4444
23
```

This was important because it suggested that the attacker was not only
scanning the perimeter --- some traffic was actually getting through.

### My conclusion

The investigation moved from **reconnaissance** to possible **initial
access/compromise**.

------------------------------------------------------------------------

# VPN Brute Force / Credential Access

Next, I checked the VPN authentication logs.

To count failed attempts by source:

``` bash
cat vpn_auth.log | grep FAIL | cut -d' ' -f3 | sort -nr | uniq -c
```

One suspicious source generated a large number of failed login attempts.

I then filtered the VPN log for the suspicious IP:

``` bash
cat vpn_auth.log | grep 203.0.113.45
```

The results showed repeated failed attempts against the same service
account followed by successful authentication.

### Targeted username

``` text
svc_backup
```

### Important observation

The attacker did not stop at failed authentication. A successful login
appeared afterwards, meaning the brute-force/credential attack
eventually resulted in access.

------------------------------------------------------------------------

# Successful VPN Access

After the successful authentication, the VPN assigned an internal
address to the attacker.

### Assigned internal IP

``` text
10.8.0.23
```

This became an important indicator because the attacker now had an
internal foothold.

The attack chain at this point was:

``` text
External attacker
      ↓
VPN brute force
      ↓
svc_backup
      ↓
Successful VPN login
      ↓
10.8.0.23
```

------------------------------------------------------------------------

# Lateral Movement

Once the attacker had an internal IP, I checked firewall logs for
connections originating from the compromised host.

``` bash
cat firewall.log | grep 10.8.0.23 | grep "ALLOW" | head
```

The traffic showed connections toward internal machines:

``` text
10.0.0.20
10.0.0.51
10.0.0.60
```

The main ports being targeted were:

``` text
22    → SSH
445   → SMB
3389  → RDP
```

This is important because the attacker was no longer only interacting
with the perimeter. They were attempting to move **inside the network**.

------------------------------------------------------------------------

# SMB Lateral Movement

I pivoted into the IDS logs to look for evidence of SMB exploitation:

``` bash
cat ids_alerts.log | grep 10.8.0.23 | grep 'SMB' | cut -d' ' -f6,7,8,9,10,19,21 | head
```

The IDS alerts contained:

``` text
EXPLOIT Possible MS-SMB Lateral Movement
```

and traffic involving:

``` text
:445
```

### Answer

``` text
445
```

Port **445** is the standard SMB port.

### My conclusion

The IDS evidence confirmed that the compromised host was attempting
SMB-based lateral movement.

------------------------------------------------------------------------

# C2 Beaconing

After finding evidence of lateral movement, I searched the IDS logs for
C2 activity:

``` bash
cat ids_alerts.log | grep C2 | head
```

The logs contained alerts such as:

``` text
ET TROJAN Possible C2 Beaconing
```

The communication repeatedly used:

``` text
:4444
```

The regular timing of the connections was also suspicious.

This pattern is consistent with **beaconing**, where a compromised host
repeatedly communicates with an attacker-controlled server.

------------------------------------------------------------------------

# Finding the C2-Compromised Host

The investigation identified the internal host responsible for the C2
beaconing.

### Answer

``` text

```

This means the workstation was communicating with an external C2
infrastructure.

------------------------------------------------------------------------

# Finding the C2 IP

I then pivoted on the compromised host to identify the external IP

The investigation identified:

# What I Learned

## 1. Logs should be correlated

One log source alone did not tell the complete story.

I had to move between:

``` text
Firewall
   ↓
VPN
   ↓
Firewall
   ↓
IDS
   ↓
Firewall / IDS
```

This allowed me to build the attack timeline.

## 2. Reconnaissance can be identified through patterns

Repeated connections to many ports from the same source are a strong
indicator of scanning.

## 3. Brute force creates a recognizable pattern

A large number of authentication failures from one source, especially
against the same account, is suspicious.

## 4. Successful authentication changes the investigation

Once the attacker received an internal IP, I had to stop thinking only
about perimeter attacks and start looking for **lateral movement**.

## 5. C2 beaconing can have a pattern

Repeated connections at regular intervals to the same external
destination can indicate malware beaconing.

## 6. Exfiltration can be detected from outbound traffic

Large HTTP POST requests and unusual outbound traffic can indicate that
data is being sent outside the organization.
