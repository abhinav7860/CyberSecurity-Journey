## 1. Introduction

Today, I learned about three common vulnerability types: **Injection (including SQL Injection), Cross-Site Scripting (XSS), and Remote Code Execution (RCE).**

The main idea behind this lesson is that vulnerabilities can occur when software trusts untrusted input or handles it incorrectly. Data supplied by a user should remain data. If an application accidentally treats that input as a command, query, or executable code, an attacker may be able to misuse the application.

This lesson focused on understanding the concepts and their impact rather than exploiting them.

## 2. The Common Root Cause: Trusting Untrusted Input

Applications receive input from users and other sources. Problems can occur when the application does not handle that input safely.

```text

        |
        v

        |
        v

        |
        v

```

The key defensive principle is to keep **data separate from instructions** and handle untrusted input safely wherever it enters or is displayed by an application.

## 3. Injection and SQL Injection

### What Is Injection?

Injection occurs when an application unintentionally treats untrusted input as part of an instruction or command instead of treating it only as data.

### What Is SQL Injection?

SQL Injection can happen when an application builds a database query by mixing user input directly into the query. If the input is handled unsafely, an attacker may be able to change how the query behaves.

**Possible impacts:**
- Exposing information stored in a database.
- Bypassing login or other application checks.
- Modifying or destroying data.

### Defensive Approach

- Keep user-supplied data separate from SQL instructions.
- Treat input as data, not instructions.
- Apply secure input-handling practices consistently.

```text

                  v
          Query may be altered

Safer principle:
User input remains data
                  |

       Query structure stays separate
```

## 4. Cross-Site Scripting (XSS)

### What Is XSS?

Cross-Site Scripting can occur when an application takes untrusted content—such as a comment, profile field, or message—and displays it to other users without handling it safely.

The browser may then interpret the content as code and execute it in another user's session.

### Potential Impact

Depending on the situation, XSS may allow an attacker to:

- Steal session-related information.
- Impersonate a user.
- Redirect users to another location.
- Manipulate what a user sees on a page.

### Defensive Approach

Applications should safely handle and display untrusted content so that it is shown as data rather than interpreted as executable code.

### SQL Injection vs. XSS

| Vulnerability | Main Issue | Potential Impact |
|---|---|---|
| SQL Injection | User input changes how a database query is interpreted | Database data or application checks may be affected |
| XSS | Untrusted content is interpreted as code in a browser | Users viewing the affected content may be affected |

Both can begin with unsafe input handling, but they affect different parts of an application.

## 5. Remote Code Execution (RCE)

### What Is RCE?

Remote Code Execution means an attacker can execute code on a system remotely without authorization.

RCE is particularly serious because the attacker may be able to perform actions available to the compromised process or account. The possible impact depends partly on the privileges and access available to that process.

RCE can arise from different weaknesses, including injection-related mistakes and memory-handling bugs.

### Why RCE Is Serious

- It can allow an attacker to run commands or code on the affected system.
- The attacker may access or change resources available to the compromised process.
- It can threaten confidentiality, integrity, and availability.
- It often leads to urgent patching because of its potential severity.

## 6. Comparing the Three Vulnerability Types

| Vulnerability | Core Problem | Possible Impact | Defensive Principle |
|---|---|---|---|
| Injection / SQL Injection | Input is handled as part of an instruction or query | Database exposure, login bypass, data modification or destruction | Keep data separate from commands |
| XSS | Untrusted content is displayed unsafely and interpreted by a browser | Session-related information theft, impersonation, redirects, altered page content | Display untrusted content safely |
| RCE | An attacker can execute code remotely without authorization | Actions permitted to the compromised process or account | Secure coding, testing, and timely patching |

## 7. Why Do These Vulnerabilities Keep Appearing?

Even when developers understand these risks, vulnerabilities can still appear because:

- Modern software is large and complex.
- Developers work under time and delivery pressure.
- A single overlooked input-handling point can introduce a weakness.
- Security practices must be applied consistently throughout an application.

Knowing about a vulnerability is not enough. Developers need to use secure coding practices, test applications, handle input safely, and apply patches when required.

## 8. The Defender's Perspective

As someone learning cybersecurity, I should focus on recognizing the underlying weakness and understanding its possible impact.

When reviewing an application or security finding, useful questions include:

1. Where does the untrusted input come from?
2. How does the application process or display that input?
3. Could the input be interpreted as a command, query, or code?
4. What data, users, or systems could be affected?
5. Is there a secure fix, test, or patch that addresses the weakness?

These questions help connect vulnerability concepts to defensive analysis and remediation.

## 10. Quick Revision

- **Injection:** Untrusted input is interpreted as part of an instruction or command.
- **SQL Injection:** Unsafe construction of database queries may let input alter query behavior.
