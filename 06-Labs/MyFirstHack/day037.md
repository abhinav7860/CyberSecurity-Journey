## The Central Nervous System of Security Operations

Yesterday ended with a major problem: IDS and IPS systems can generate thousands of alerts, and important threats can get buried in the noise.

A real organisation has many systems generating logs and alerts:

- IDS/IPS
- Firewalls
- Servers
- Endpoints
- Cloud services
- Applications
- Authentication systems

Checking every system separately makes it difficult to see the bigger picture.

This is where a **SIEM** comes in.

**SIEM = Security Information and Event Management**

A SIEM collects security-related logs and alerts from across an organisation, puts them in one place, makes them searchable, and correlates events from different sources.

I think of a SIEM as the **central nervous system of a Security Operations Centre (SOC)**.

### Why correlation matters

One failed login might mean nothing.

```text
1 failed login       → Probably normal
50 failed logins     → Suspicious
50 failures + success
from the same source → Possible compromise
```

The SIEM can see the bigger pattern instead of treating every event as an isolated alert.

### Takeaway

- **IDS:** Detects suspicious traffic and alerts.
- **IPS:** Detects suspicious traffic and can also block it.
- **SIEM:** Collects and correlates security events from many systems.
- The SIEM helps turn scattered security data into investigable incidents.

# What a SIEM Actually Does

A SIEM performs several important functions.

## 1. Collection

The SIEM collects security-relevant data from across the organisation.

Common sources include:

- Firewalls
- IDS/IPS
- Servers
- Workstations
- Cloud platforms
- Applications
- Authentication systems

A large organisation can send huge numbers of events to a SIEM every second.

The goal is to make sure important security activity is recorded centrally.

---

## 2. Normalisation

Different systems record events in different formats.

For example:

- Windows uses one log format.
- Linux uses another.
- Cisco firewalls use another.
- Cloud services use their own structures.

Even something simple like a login can have different field names, timestamps, and structures.

The SIEM **normalises** these events into a common structure.

```text
Windows Log ─────┐
Linux Log ───────┤
Firewall Log ────┼──→ SIEM → Common Format
Cloud Log ───────┤
Application Log ─┘
```

Normalisation makes it possible to search and compare events from different systems.

---

## 3. Correlation

**Correlation is the heart of a SIEM.**

The SIEM looks for relationships between events.

A single event may not look suspicious, but multiple related events can reveal an attack.

Example:

```text
Login from new country
        ↓
Sensitive file access
        ↓
Large outbound transfer
        ↓
Possible data breach
```

Each event individually may be normal. Together, they tell a very different story.

---

## 4. Alerting and Dashboards

When a correlation rule identifies suspicious activity, the SIEM can generate an alert.

The SIEM can also prioritise alerts so serious incidents receive attention first.

Dashboards allow SOC analysts to see:

- Current alerts
- Security trends
- Events by severity
- Systems generating activity
- Areas requiring investigation

---

## 5. Search and Investigation

A SIEM stores a searchable history of security events.

During an investigation, an analyst can ask:

> What did this user account do across all systems during the last 24 hours?

Instead of checking every server separately, the analyst can search the SIEM and investigate events from many different sources.

### SIEM workflow

```text
Collection
    ↓
Normalisation
    ↓
Correlation
    ↓
Alerting
    ↓
Investigation
```

# Correlation: The Power of a SIEM

Correlation is what separates a SIEM from a simple log collector.

## Brute Force Detection

A single failed login is not very interesting.

But:

```text
50 failed logins
      ↓
Within 2 minutes
      ↓
Successful login
```

can indicate that an account was brute-forced and then accessed.

A correlation rule can count failed attempts over a specific period.

---

## Credential Stuffing

Credential stuffing can be detected by looking across many accounts.

```text
One IP
  ↓
Account 1 → Failed
Account 2 → Failed
Account 3 → Success
Account 4 → Failed
Account 5 → Success
```

The individual attempts may not look unusual, but the spread across many accounts from one source is suspicious.

---

## Impossible Travel

A SIEM can combine geographic information with login times.

```text
10:00 → Successful login from London
10:10 → Successful login from Singapore
```

The credentials may be valid, but the travel time is impossible.

This can indicate that stolen credentials are being used.

---

## Full Attack Chain Correlation

The SIEM can also connect activity from multiple systems:

```text
Phishing Email
      ↓
Login from New Device
      ↓
Internal Network Scanning
      ↓
Sensitive Database Access
      ↓
Large Outbound Transfer
      ↓
Possible Data Exfiltration
```

These events may come from:

- Mail security logs
- Authentication logs
- IDS logs
- Database logs
- Firewall logs

Without a SIEM, an analyst might see five unrelated alerts.

With correlation, the SIEM can connect them into one attack story.

### Takeaway

Correlation allows a SIEM to turn isolated events into a complete incident.

# The Limits and Cost of SIEMs

A SIEM is powerful, but it is not magic.

## 1. A SIEM Is Only as Good as What Feeds It

If a system does not send logs to the SIEM, the SIEM cannot see what is happening there.

```text
Critical Server
      ↓
No Logs Sent
      ↓
SIEM
      ↓
No Visibility
```

Missing log sources can create major blind spots.

Organisations need to continuously verify that important systems are actually sending their logs.

---

## 2. A SIEM Is Only as Good as Its Rules

Correlation does not happen automatically.

Someone needs to create and maintain rules that define which patterns should generate alerts.

For example:

```text
50 failed logins
within 2 minutes
      ↓
Generate Alert
```

Threats change over time, so correlation rules need to change too.

---

## 3. False Positives Still Exist

The SIEM does not magically remove the false-positive problem from Day 36.

A poorly tuned SIEM can generate huge numbers of low-value alerts.

```text
Too Many Alerts
      ↓
Analyst Overload
      ↓
Important Alert Gets Missed
```

SOC teams therefore spend time tuning SIEMs by:

- Suppressing known benign events
- Adjusting thresholds
- Improving correlation rules
- Prioritising important events
- Reducing unnecessary alerts

SIEM tuning is an ongoing process.

---

## 4. SIEMs Can Be Expensive and Complex

Enterprise SIEMs can be expensive.

Licensing can depend heavily on the amount of data being ingested. More logs can mean higher costs.

SIEM platforms also require skilled people to:

- Configure them
- Maintain them
- Write detection rules
- Tune alerts
- Investigate incidents

A SIEM is a **force multiplier**, not a replacement for security professionals.

### Takeaway

A SIEM requires:

- Good log sources
- Good correlation rules
- Continuous tuning
- Skilled analysts
- Budget and infrastructure

# Major SIEM Platforms

## Splunk

Splunk is one of the most well-known SIEM platforms.

It is powerful and widely used in enterprise security operations, but it is also known for being expensive.

## Microsoft Sentinel

Microsoft Sentinel is a cloud-native SIEM associated with Microsoft's Azure ecosystem.

## Elastic Security / ELK Stack

Elastic Security is built around the Elastic Stack, commonly referred to as the **ELK stack**.

It is a popular option and can be more accessible for learners who want to practise SIEM concepts themselves.

## IBM QRadar

IBM QRadar is another enterprise SIEM platform.

## Google Chronicle

Google Chronicle is another enterprise security platform used for security monitoring and analysis.

```text
Splunk
Microsoft Sentinel
Elastic Security / ELK
IBM QRadar
Google Chronicle
```

# SOAR: The Evolution Beyond SIEM

**SOAR = Security Orchestration, Automation, and Response**

A SIEM mainly helps detect, correlate, prioritise, and investigate events.

SOAR takes this further by automating responses.

For example:

```text
SIEM detects compromise
        ↓
SOAR playbook starts
        ↓
Isolate affected machine
        ↓
Disable compromised account
        ↓
Block malicious IP
        ↓
Open incident ticket
```

Instead of waiting for an analyst to perform every routine action manually, SOAR can automate the response.

This is similar to the IDS vs IPS distinction from Day 36, but at the incident-response level:

```text
SIEM → Detect and Alert

SOAR → Automate Response
```

Automation allows security analysts to spend more time on complex investigations and judgement calls.

# SIEM and Small Businesses

A small business like Maya's probably won't run a large enterprise SIEM such as Splunk itself.

However, SIEM technology can still protect the business indirectly.

Cloud providers and services may have their own security monitoring systems.

As the business grows, a practical option can be a **Managed Detection and Response (MDR)** service.

Instead of buying and operating the entire SIEM infrastructure, a provider can operate the monitoring system and provide security monitoring as a service.

The lesson for a small business is not necessarily to buy a SIEM, but to understand that centralised security monitoring exists and consider managed security services as the organisation grows.

# Important Terms

## SIEM

**Security Information and Event Management**

Centralises logs and alerts and correlates events across different sources.

## Normalisation

Converting different log formats into a common structure.

## Correlation

Connecting multiple events to identify meaningful patterns.

## Alert Fatigue

When too many alerts make it difficult for analysts to identify important threats.

## SOAR

**Security Orchestration, Automation, and Response**

Automates security response actions based on detected events.

## MDR

**Managed Detection and Response**

A managed service where security monitoring and response capabilities are provided by an external provider.

## SOC

**Security Operations Centre**

The team and operational environment responsible for monitoring and responding to security events.

# Key Takeaways

- **SIEM = Security Information and Event Management.**
- A SIEM acts as a central security monitoring system for a SOC.
- It collects logs and alerts from many different systems.
- Normalisation converts different log formats into a common structure.
- Correlation connects multiple events to identify meaningful attack patterns.
- SIEM dashboards help analysts monitor security activity.
- Search capabilities make SIEMs useful for investigations and incident response.
- Brute force, credential stuffing, impossible travel, and multi-stage attacks can be detected through correlation.
- A SIEM is blind to systems that are not sending logs.
- Poor correlation rules can cause attacks to be missed.
- Poor tuning can create large numbers of false positives.
- Enterprise SIEMs can be expensive and complex.
- Important SIEM platforms include Splunk, Microsoft Sentinel, Elastic Security, IBM QRadar, and Google Chronicle.
- **SOAR** extends SIEM capabilities by automating security responses.
- Smaller organisations can use managed services such as MDR instead of running a full SIEM themselves.
