# 1. Why Suspicious File Investigation Matters

Investigating an unknown file is a realistic security task.

A:

- SOC analyst
- Incident responder
- Malware analyst

may encounter an unknown or suspicious file during an investigation.

The first step is not automatically to run it. Instead, the analyst carefully examines the file to understand what it is and what it might do.

```text
Unknown / Suspicious File
          |
          v
     Examine Safely
          |
          +-- Identify type
          +-- Check properties
          +-- Read contents
          +-- Search for red flags
          |
          v
       Reach Verdict
          |
          v
     Make Recommendation
```

---

# 2. The Questions to Ask

A suspicious-file investigation can be broken into a sequence of questions.

| Question | Tool |
|---|---|
| What kind of file is it? | `file` |
| What are its properties? | `ls -l` |
| What's inside a text/script file? | `cat`, `less`, `head`, `tail` |
| What's inside a binary? | `strings` |
| Are there suspicious things inside? | `grep` |

Together, these tools build a picture of the file without executing it.

---

# 3. Identify the File Type with `file`

The first question is:

> **What kind of file is this?**

Use:

```bash
file filename
```

The `file` command examines the actual contents of a file and reports its type.

This matters because a filename can be misleading. For example, a file called `invoice.pdf` might actually contain a program.

The command looks at the real contents/signature rather than simply trusting the filename.

Knowing the type determines how the investigation should continue.

---

# 4. Check File Properties with `ls -l`

The next question is:

> **What are the file's properties?**

Use:

```bash
ls -l filename
```

This shows useful information such as:

- Permissions
- Owner
- File size
- Modification time

Each property can provide a clue.

### Permissions

Pay attention to whether the file has the `x` permission.

```text
x = executable
```

A suspicious executable deserves more attention than a plain text file.

### Owner

The owner can help establish who the file belongs to.

### Modification time

The modification time can be compared with the timeline of a suspicious event.

---

# 5. Read the Contents

Once the file type and properties are known, the next question is:

> **What's inside it?**

For text files and scripts, the contents can be read directly with:

```bash
cat filename
```

```bash
less filename
```

```bash
head filename
```

```bash
tail filename
```

For a script, reading the contents can reveal what the script would do if it were executed.

---

# 6. Reading a Script Like an Investigator

A script is a text file containing commands. That makes it possible to inspect its behaviour without executing it.

Every line can provide information about the script's intended actions.

```text
Script
  |
  +-- Command 1
  +-- Command 2
  +-- Command 3
  +-- Command 4
        |
        v
   Intended behaviour
```

A benign script might:

- Back up files
- Print a message
- Perform another legitimate task

A malicious script could reveal dangerous behaviour directly in its commands.

When reading a script, ask:

> **What is this line trying to do, and should a legitimate file be doing that?**

---

# 7. Red Flags in a Suspicious Script

Important red flags from today's lesson include:

### 1. Downloading and running something

A script that reaches out to the internet, downloads something, and then runs it is a classic malware pattern.

```text
Internet
   |
   v
Download payload
   |
   v
Execute payload
```

This can indicate a **fetch-a-payload** pattern.

### 2. Modifying system files or permissions

Be suspicious of commands that modify system files or permissions, especially when they weaken security.

### 3. Creating user accounts

Creating or modifying accounts can be used by attackers for persistence. This connects to the user/account concepts from **Day 52**.

### 4. Touching logs

Commands that modify or clear logs can indicate an attempt to hide activity or cover tracks.

### 5. Seeking elevated privileges

Commands that attempt to run with elevated privileges deserve attention because they may allow actions requiring greater permissions.

### 6. Obfuscation

Obfuscated or deliberately scrambled/encoded content is itself a red flag because it can hide behaviour.

You do not need to be a scripting expert. The important skill is reading each line and considering whether its behaviour makes sense for a legitimate file.

---

# 8. Use `strings` on Binary Files

Not every suspicious file is a readable script. A compiled program is a binary and may not be human-readable.

For these files:

```bash
strings filename
```

extracts readable text embedded inside the binary.

This can reveal useful information such as:

- Web addresses
- Commands
- Messages
- File paths

The important point is that `strings` lets me inspect meaningful content **without running the binary**.

```text
Binary File
     |
     v
  strings
     |
     v
Readable text
     |
     +-- URLs
     +-- Commands
     +-- Messages
     +-- File paths
```

---

# 9. Search for Red Flags with `grep`

After obtaining readable content, I can search it for things that deserve attention.

Use:

```bash
grep "pattern" filename
```

Possible investigation targets include:

- Web addresses
- IP addresses
- Suspicious commands
- Password references
- System-file references
- Other signs of network or sensitive-system activity

`grep` makes it possible to scan for specific indicators without manually reading every line.

# 10. The Complete Safe Investigation Sequence

The investigation can be remembered as:

```text
1. Identify
      |
   file

2. Check properties
      |
   ls -l

3. Read contents
      |
   cat / less / head / tail
      OR
   strings

4. Search for red flags
      |
   grep

5. Reach a verdict
      |
   Benign / Suspicious / Malicious

6. Recommend an action
```

This sequence gives a structured way to examine an unknown file.

---

# 11. Never Run the Unknown File

The central safety rule of this lesson is:

> **Examine first. Do not execute an unknown suspicious file.**

Reading a script:

```bash
cat suspicious.sh
```

is fundamentally different from running it.

The purpose of today's investigation is to understand the file while it remains inactive.

This connects directly to **Day 51**, where removing execute permission can neutralise a file without deleting it.

A suspicious script can therefore be retained as evidence while its execute permission is removed, allowing it to be studied without running it.

```text
Suspicious File
      |
      v
Remove execute permission
      |
      v
Preserve as evidence
      |
      v
Study safely
```

---

# 12. Reaching an Honest Verdict

Investigation is not finished until a conclusion is reached.

The three valid verdicts are:

### Benign

The file was examined and appears to perform legitimate, harmless actions. The conclusion should explain why.

### Malicious

There is specific evidence showing dangerous behaviour. The conclusion should name the behaviour precisely.

For example:

```text
The file is malicious because it downloads a file
from an unfamiliar web address and runs it with
elevated privilege.
```

### Suspicious / Uncertain

Sometimes the evidence is concerning, but the investigation cannot completely determine the file's purpose. That is also a valid conclusion.

```text
The file contains several concerning behaviours,
but its full purpose could not be confirmed.
```

Being honest about uncertainty is part of professional investigation.

---

# 13. Evidence-Based Reasoning

A weak conclusion is:

```text
"This file looks scary."
```

A stronger conclusion is:

```text
"This file is malicious because it contains a command
that downloads a file from an unfamiliar web address
and runs it with elevated privilege."
```

The second conclusion is stronger because it identifies:

1. What was observed
2. Why it matters
3. How the evidence supports the verdict

```text
Observation
    |
    v
Interpretation
    |
    v
Evidence-based Verdict
```

This is the same precision used in the earlier **Day 35 traffic investigation**.

---

# 14. Verdict -> Recommendation

The verdict should lead to an action.

| Verdict | Recommendation |
|---|---|
| Benign | Document why it is legitimate and move on |
| Suspicious / Uncertain | Investigate further with more advanced analysis |
| Malicious | Do not run it, preserve it as evidence, and escalate it |

For a malicious file, the lesson specifically connects preservation to the earlier permissions work:

```text
Malicious file
     |
     v
Do not execute
     |
     v
Remove execute permission
     |
     v
Preserve as evidence
     |
     v
Escalate
```

The investigation therefore produces both:

- An understanding of the file
- A decision about what should happen next

# What I Learned

Day 56 was the first Linux capstone, and it brought together the skills from the previous days.

I learned that:

- A suspicious file should be examined before anything else.
- The `file` command can identify the actual type of a file.
- `ls -l` provides important file properties such as permissions, owner, size, and modification time.
- Text files and scripts can be safely examined with `cat`, `less`, `head`, and `tail`.
- `strings` can extract readable text from binaries without executing them.
- `grep` can search file contents for potential red flags.
- Suspicious scripts should be read line by line to understand their intended behaviour.

- Benign, malicious, and suspicious/uncertain are all valid investigation outcomes.
- The recommendation should follow from the evidence and verdict.
- Removing execute permission can help preserve a suspicious file as evidence without running it.
- Safe examination is more important than immediately executing an unknown file.

The main principle I want to remember is:

> **Read and examine first. Never run an unknown suspicious file just to find out what it does.**
