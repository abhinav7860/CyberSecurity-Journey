# 1. Why Network Visibility Matters

When a machine is suspected of being compromised, two important
questions are:

``` text
What's running?
      ↓
Processes
      ↓
What's it talking to?
      ↓
Network connections
```

A malicious process may receive commands, send stolen data, contact an
attacker, or periodically check in.

This means network connections can provide important evidence about what
a suspicious process is doing.

The terminal makes it possible to inspect this activity directly from
the machine without requiring Wireshark or access to network equipment.

------------------------------------------------------------------------

# 2. `ss` and `netstat`

The main tool introduced today is:

``` bash
ss
```

`ss` stands for **socket statistics**.

It is the modern command for viewing the machine's live network state.

The older classic command is:

``` bash
netstat
```

Both can show network connections and listening ports.

------------------------------------------------------------------------

# 3. Established Connections

An **established connection** represents active communication between
the local machine and another machine.

A connection contains information such as:

-   Local address
-   Local port
-   Remote address
-   Remote port

This answers:

> **What is this machine connected to right now?**

``` text
Local Machine
     │
     │ connection
     ▼
Remote Machine
```

Each active connection can become an investigation point.

------------------------------------------------------------------------

# 4. Listening Ports

A **listening port** belongs to a service waiting for incoming
connections.

For example:

``` text
Web service → port 443
SSH service → port 22
```

A listening port answers:

> **What is this machine offering to the network?**

Together, established connections and listening ports provide a picture
of the machine's network state.

``` text
Network State
      │
      ├── Established connections
      │      ↓
      │   What is it talking to?
      │
      └── Listening ports
             ↓
        What is it offering?
```

------------------------------------------------------------------------

# 5. Connecting Network Activity to Processes

A useful form of `ss` can show the program using a connection or
listening port.

This is important because it connects today's lesson to Day 57.

``` text
Network Connection
        ↓
Which process owns it?
        ↓
Investigate the process
```

This lets an investigator move from a suspicious connection to the
process responsible for it.

# 6. Security Signs in Network Activity

Several network behaviours can deserve investigation.

### Unrecognised listening port

A listening port that no legitimate service should have open may
indicate a backdoor.

### Unfamiliar external connection

A connection to an unfamiliar external address can be a clue. It could
potentially represent data exfiltration, command and control, or other
unwanted communication.

### Repeated connections

Repeated connections to the same external address at regular intervals
can resemble the **beacon** pattern learned in Day 32.

``` text
Process
   ↓
Connect
   ↓
Wait
   ↓
Connect again
   ↓
Repeat
```

This can indicate malware checking in.

### Important

None of these signs is automatically proof of malicious activity.

They are clues that should be investigated further.

# 7. `ping`

`ping` tests whether another machine is reachable across the network and
gives an indication of response time.

Example:

``` bash
ping 8.8.8.8
```

It can also be used with a name.

It answers:

> **Can I reach this, and is the connection alive?**

If responses are received, basic connectivity to that destination works.

If there is no response, the destination could be down, unreachable, or
configured not to respond to ping.

Therefore:

> **No ping response does not always mean the destination is down.**

`ping` is useful for basic connectivity troubleshooting.

------------------------------------------------------------------------

# 8. `dig`

`dig` is a terminal tool for performing DNS lookups.

This connects directly to the DNS concepts from Day 24.

Example:

``` bash
dig example.com
```

It queries DNS and displays information about the response, including
the IP address a name resolves to, DNS server information, and record
details.

The main question is:

> **What does this domain actually resolve to?**

``` text
Domain name
     ↓
    dig
     ↓
DNS response
     ↓
Resolved address/details
```

------------------------------------------------------------------------

# 9. Why DNS Investigation Matters

A suspicious process may contact a domain name.

Using `dig`, I can check what that name resolves to.

This also connects to the earlier lesson about **DNS spoofing (Day
33)**.

A falsified DNS answer can send a system somewhere it did not intend to
go.

``` text
Suspicious domain
       ↓
      dig
       ↓
Check DNS response
       ↓
Understand where it points
```

`nslookup` is another DNS lookup tool, but the lesson focuses on `dig`
as the more capable modern option.

# 10. The Three Main Network Tools

  Tool     Purpose
  -------- ---------------------------------------------------
  `ss`     View live network connections and listening ports
  `ping`   Test reachability
  `dig`    Perform DNS lookups

An older related tool is:

``` bash
netstat
```

# 11. Spotting a Process Phoning Home

This is the main investigative payoff of Day 58.

The idea is to combine yesterday's process investigation with today's
network investigation.

Imagine a machine is compromised. The malware is running as a process
and communicating with an attacker.

``` text
Running process
      ↓
Network connection
      ↓
Unfamiliar external address
      ↓
Investigate responsible process
      ↓
Connect process + network activity
```

This is the local equivalent of the beacon behaviour studied in Day 32.

# 12. Signs of a Possible Beacon

A possible beacon can appear as:

``` text
Connection
     ↓
Wait
     ↓
Connection
     ↓
Wait
     ↓
Connection
```

Other signs include:

-   An unfamiliar external IP
-   A listening port that should not be open
-   A suspicious process making network connections
-   A process with no clear reason to communicate over the network

Each sign is a thread to investigate rather than automatic proof of
compromise.

# 13. The Investigation Loop

The investigation combines Days 57 and 58.

``` text
1. What's running?
        ↓
     ps aux
        ↓
2. Is anything suspicious?
        ↓
3. What is it connected to?
        ↓

        ↓

```

The process and network views reinforce each other.

# 17. Practical Investigation Mindset

When looking at a network connection, ask:

``` text
What is this connection?
        ↓
Who is it communicating with?
        ↓
What port is being used?
        ↓
Which process owns it?
        ↓
Should this communication exist?
        ↓
Can I explain it?
```

The goal is not to label every unfamiliar connection as malicious.

The goal is to understand what is normal and investigate what does not
fit.
