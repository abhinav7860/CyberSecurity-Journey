## Overview

Today I learned about **Linux hardening** and how the different security practices I have learned throughout this phase come together into one defensive discipline.

Hardening means making a system as resistant to attack as possible by deliberately reducing the ways it can be compromised **before an attack happens**.

The main idea is **proactive defence**.

```text
Investigation
    ↓
Find what went wrong

Hardening
    ↓
Reduce the chances of it going wrong
```

A hardened system is not impossible to compromise, but it is much harder to attack successfully than an unhardened system.

---

# 1. What Is Hardening?

Hardening is the practice of making a system more resistant to attack.

The goal is to:

- Reduce weaknesses
- Reduce unnecessary access
- Remove unnecessary components
- Limit privileges
- Secure remote access
- Keep software updated
- Monitor the system
- Reduce possible ways an attacker can enter

The important distinction is:

```text
Hardening = Before compromise
Investigation = After / during suspicious activity
```

Hardening is like putting strong locks on a building before someone attempts to break in.

---

# 2. Why Hardening Matters

Many real-world attacks do not require extremely sophisticated techniques.

Attackers often take advantage of:

- Unpatched software
- Weak authentication
- Excessive privileges
- Unnecessary services
- Unused software
- Unnecessary accounts
- Open network ports
- Poorly protected files

Hardening addresses these weaknesses before an attacker can easily exploit them.

The goal is not:

```text
100% Secure
```

because that is unrealistic.

The goal is:

```text
Make compromise harder
        +
Limit the impact
        +
Detect what gets through
```

---

# 3. Attack Surface

The central concept behind hardening is the **attack surface**.

Attack surface means the collection of ways an attacker could potentially attack or enter a system.

This can include:

- Services
- User accounts
- Installed software
- Open ports
- Authentication mechanisms
- Other exposed components

Conceptually:

```text
              SYSTEM
                 |
      ┌──────────┼──────────┐
      ↓          ↓          ↓
   Services   Accounts   Software
      ↓          ↓          ↓
   Open Ports / Other Entry Points
                 ↓
            Attack Surface
```

The larger the attack surface, the more opportunities an attacker has.

The smaller the attack surface, the fewer opportunities exist.

---

# 4. Reducing Attack Surface

Hardening fundamentally means reducing the attack surface.

For example:

### Unnecessary service

```text
Unused service
      ↓
Potential vulnerability
      ↓
Turn it off
      ↓
Smaller attack surface
```

### Unused software

```text
Unused software
      ↓
Possible vulnerability
      ↓
Remove it
      ↓
Smaller attack surface
```

### Unnecessary account

```text
Unnecessary account
      ↓
Possible entry point
      ↓
Remove it
      ↓
Smaller attack surface
```

### Unnecessary port

```text
Open port
      ↓
Possible network entry point
      ↓
Close if not required
      ↓
Smaller attack surface
```

The general question is:

> **Does this need to be here, and if it does, how can I make it safer?**

# 6. Core Hardening Actions

Today's lesson gathered the main hardening actions into one checklist.

## 6.1 Keep Software Updated

Security updates should be applied promptly.

Unpatched software can contain known vulnerabilities that attackers may already know how to exploit.

This connects directly to **Day 60 — Package Managers**.

```text
Known vulnerability
       ↓
Security update available
       ↓
Apply update
       ↓
Reduce exposure
```

Keeping software updated is one of the most effective basic security practices.

---

## 6.2 Apply Least Privilege

Users, processes, and services should have only the access they actually need.

This means:

- Avoid unnecessary root access
- Use tight file permissions
- Limit sudo access
- Avoid giving excessive privileges

The principle is:

```text
Required privilege
      ↓
Grant only that
      ↓
Nothing unnecessary
```

Every privilege that is not granted is one less privilege an attacker can abuse.

This connects with the permission and user-management lessons from Days 51–52 and earlier least-privilege lessons.

---

## 6.3 Remove What You Don't Need

Remove unnecessary components such as:

- Unused software
- Unnecessary services
- Accounts that should not exist

Each removal reduces the attack surface.

```text
Unused service
      ↓
Provides no benefit
      +
Creates possible risk
      ↓
Disable/remove it
```

This is why software hygiene is also part of hardening.

---

## 6.4 Secure Remote Access

SSH is an important access point, so it needs to be hardened.

From **Day 63**, important SSH security practices include:

- Prefer SSH keys over passwords
- Avoid direct root login
- Limit who can connect
- Monitor authentication logs
- Reduce unnecessary exposure

SSH is a powerful doorway into a Linux system.

Therefore:

> **The most powerful access points deserve the most protection.**

---

## 6.5 Monitor and Log

Hardening is about prevention, but prevention is not enough.

Systems should also record activity and be monitored.

This connects with **Day 59 — Reading Logs**.

```text
Hardening
    ↓
Prevent what can be prevented

Monitoring
    ↓
Notice what gets through
```

This creates a stronger defensive approach.

---

## 6.6 Use a Firewall

A firewall controls which network connections a system accepts.

The basic idea is:

```text
Incoming connection
        ↓
Firewall
        ↓
Is it needed?
    ↙       ↘
  Yes        No
   ↓          ↓
 Allow       Block
```

A firewall complements the reduction of open ports and network exposure.

Only connections that are actually needed should be allowed.

# 8. Defence in Depth

Another major concept from today's lesson is **defence in depth**.

Defence in depth means not depending on one security control.

Instead, multiple layers protect the system.

For example:

```text
        Attacker
           ↓
      ┌───────────┐
      │ Firewall  │
      └─────┬─────┘
            ↓
      ┌───────────┐
      │   SSH     │
      │ Hardening │
      └─────┬─────┘
            ↓
      ┌───────────┐
      │   Least   │
      │ Privilege │
      └─────┬─────┘
            ↓
      ┌───────────┐
      │ Monitoring│
      │   / Logs  │
      └─────┬─────┘
            ↓
         Backups
```

If one layer fails, another layer can still provide protection.

---

# 9. Example of Defence in Depth

Imagine SSH security is bypassed.

That does not automatically mean the attacker gets unlimited control.

Other layers may still help:

```text
SSH compromise
      ↓
Least privilege limits access
      ↓
Firewall limits network paths
      ↓
Logs record activity
      ↓
Monitoring detects suspicious behaviour
      ↓
Backups support recovery
```

This is much stronger than relying on a single defence.

# 11. Limits of Hardening

Hardening reduces risk, but it does **not** eliminate risk.

There is no perfectly secure system.

New vulnerabilities can be discovered.

Attackers can also have different levels of:

- Skill
- Time
- Resources
- Motivation

Therefore, the realistic goal is not:

```text
Impossible to compromise
```

It is:

```text
Harder to compromise
+
More expensive to attack
+
More likely to detect
+
Better ability to recover
```

Security is about managing risk to an acceptable level.

Hardening is the **prevention** part of security.

But a mature defensive approach also needs:

```text
Prevention
```

In this phase:

```text
Hardening
    ↓
Prevention

Logs / Monitoring
    ↓
Detection

    ↓

```

Because hardening cannot guarantee prevention, detection and investigation are still necessary.

# 13. The Three Defensive Stages

## Prevention

Make compromise harder.

Examples:

- Hardening
- Least privilege
- Updates
- Firewall
- Secure SSH

## Detection

Notice suspicious activity.

Examples:

- Logs
- Monitoring
- Process investigation
- Network monitoring

## Response

Investigate and deal with what happened.

Examples:

- Examine processes
- Analyse network connections
- Review logs
- Find persistence
- Investigate compromised files

Together:

```text
PREVENT
   ↓
DETECT
   ↓
RESPOND
```

# 15. Hardening vs Investigation

There is a useful symmetry between the two.

### Investigation

```text
System
  ↓
Find what is wrong
  ↓
Understand the compromise
```

### Hardening

```text
System
  ↓
Remove weaknesses
  ↓
Reduce the chance of compromise
```

So:

```text
Hardening = Prevent
Investigation = Understand / Respond
```

Both are necessary in practical cybersecurity.
