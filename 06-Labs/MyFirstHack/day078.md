## 1. Introduction

Today, I learned how organisations manage the constant flood of software vulnerabilities. A vulnerability is a weakness that an attacker may exploit. Since new vulnerabilities are discovered continually and organisations run many different applications, libraries, operating systems, and devices, vulnerability management cannot be treated as a one-time task.

**Vulnerability management** is the systematic process of discovering, assessing, prioritising, and fixing vulnerabilities. It applies the risk-based thinking from Day 67: because an organisation cannot fix everything at once, it needs to identify which vulnerabilities matter most and address those first.

This lesson introduced three key ideas:

- **CVE:** A shared identifier for a publicly known vulnerability.
- **CVSS:** A standardised score describing vulnerability severity.
- **Vulnerability management lifecycle:** A continuous process of discovery, prioritisation, remediation, and verification.

## 2. CVE: A Name for Every Vulnerability

**CVE** stands for **Common Vulnerabilities and Exposures**. It is a global system that gives publicly known vulnerabilities unique identifiers so researchers, software vendors, defenders, and security tools can refer to the same vulnerability unambiguously.

A CVE identifier has a format such as `CVE-2024-12345`. It lets scanners, vendors, and security reports refer to the same specific vulnerability without relying on inconsistent descriptions.

### Why CVE matters

- Vulnerability scanners can report which CVEs affect systems.
- Vendors can identify which CVEs their updates address.
- Defenders can look up vulnerabilities and assess whether they affect their environment.
- Teams can communicate consistently about the same weakness.

This is similar to the common language provided by MITRE ATT&CK (Day 72), which gives standard names to attacker techniques. CVE provides consistent identifiers for vulnerabilities.

### Responsible disclosure

The lesson also introduced responsible disclosure. A researcher who discovers a vulnerability may report it privately to the vendor first, giving the vendor time to prepare a fix before the weakness is made public. The goal is to balance public awareness with reducing the risk of attackers exploiting a vulnerability before defenders have a fix.

## 3. CVSS: How Severe Is It?

**CVSS** stands for **Common Vulnerability Scoring System**. It provides a severity score from **0 to 10**, with higher scores indicating greater severity.

The score considers factors such as:

- How easy the vulnerability is to exploit.
- Whether an attacker can exploit it remotely or needs special access or conditions.
- How much damage exploitation could cause.

The lesson groups severity into four broad bands:

| Severity | General meaning |
|---|---|
| Critical | Most severe; typically needs urgent attention |
| High | Serious severity |
| Medium | Moderate severity |
| Low | Lower severity |

CVSS helps security teams compare vulnerabilities and make an initial judgement about urgency.

### Severity is not the same as your actual risk

A CVSS score does not tell the whole story about risk in a specific organisation. Actual risk also depends on context:

- Does the organisation use the affected software?
- Is the affected system exposed to potential attackers or isolated?
- Does the system contain valuable information or provide an important service?

For example, a critical-severity vulnerability in software an organisation does not use may not create a direct risk for that organisation. A medium-severity vulnerability in an internet-facing customer database could be more important to address than a critical-severity issue on an isolated test machine.

This connects to Day 67: severity is an important input, but risk-based prioritisation must also consider the organisation's environment.

## 4. The Vulnerability Management Lifecycle

Vulnerability management is a continuous cycle. The core stages described in the lesson are:

```text
+-----------+
| Discover  |
+-----+-----+
      |
      v
+-----------------------+
| Assess and Prioritise |
+-----------+-----------+
            |
            v
+------------+
| Remediate  |
+------+-----+
       |
       v
+----------+
| Verify   |
+----+-----+
     |
     v
 Repeat continuously
```

### Stage 1: Discover

Find vulnerabilities affecting systems in the environment. Vulnerability scanners can check systems against known vulnerabilities and report which CVEs may affect which systems.

The starting point is visibility: an organisation cannot manage weaknesses it does not know about.

### Stage 2: Assess and prioritise

Evaluate each finding using its CVSS severity and the context of the affected system. This helps create an ordered list of what should be addressed first.

Prioritisation is central because organisations usually have limited time and resources.

### Stage 3: Remediate

Fix or reduce the vulnerability's risk. The lesson identifies several possible approaches:

- **Patching:** Apply the vendor's update, connecting to Day 60's lesson on package managers and software maintenance.
- **Configuration change:** Correct an insecure setting.
- **Workaround:** Use a temporary measure when an immediate full fix is not available.
- **Risk acceptance:** Accept a sufficiently low risk when appropriate, following the organisation's risk process.

### Stage 4: Verify

Confirm that the fix worked and the vulnerability is no longer present. Re-scanning can help verify the result.

### Stage 5: Repeat

The cycle continues because new vulnerabilities are discovered and environments change as software is added or systems are reconfigured. Vulnerability management is ongoing maintenance, not a project that is permanently finished.

## 5. Prioritising Vulnerabilities in Practice

The central judgement in vulnerability management is deciding what to fix first when there are too many findings to address simultaneously.

| Finding context | General prioritisation consideration |
|---|---|
| High severity, affects the organisation, and is exposed to attackers | Strong candidate for urgent remediation |
| Lower severity on an isolated system with limited value | May be lower priority, depending on context |
| Vulnerability in software the organisation does not use | May not represent a direct risk to that environment |

These are general considerations, not automatic rules. The organisation still needs to confirm whether the affected software and system are present and assess the actual context.

**Important distinction:** CVSS describes general vulnerability severity. Risk-based prioritisation combines severity with information about the organisation's own systems, exposure, and the value of the assets involved.

This is the judgement the lesson connects to the vulnerability triage capstone on Day 80.

## 7. Quick Revision

- **Vulnerability management:** The systematic, continuous process of finding, assessing, prioritising, and fixing vulnerabilities.
- **CVE:** Common Vulnerabilities and Exposures; a unique identifier for a publicly known vulnerability.
- **CVSS:** Common Vulnerability Scoring System; a severity score from 0 to 10.
- **Severity:** How serious a vulnerability is in general.
- **Actual risk:** Depends on severity and the specific environment, including software use, exposure, and asset value.
- **Discover:** Find vulnerabilities affecting systems.
- **Assess and prioritise:** Decide which findings matter most.
- **Remediate:** Patch, change configuration, apply a workaround, or follow an appropriate risk-acceptance process.
- **Verify:** Confirm the fix worked.
- **Repeat:** Continue because vulnerabilities and environments change over time.

## 8. What I Learned

Today, I learned how CVE identifiers and CVSS scores support vulnerability management. CVE gives everyone a consistent way to refer to a known vulnerability, while CVSS provides a standardised view of its general severity.

I also learned that a severity score alone cannot determine what an organisation should fix first. The organisation must consider whether it uses the affected software, how exposed the system is, and how valuable the affected asset is.

The most important practical lesson is that vulnerability management is a continuous cycle: discover, assess and prioritise, remediate, verify, and repeat.

## 10. Conclusion

Day 78 helped me understand the systems and workflow organisations use to keep known vulnerabilities under control.
