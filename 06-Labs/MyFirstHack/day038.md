## The Foundation Under Everything

For the last two days, I was one level up:

- Day 36 → IDS and IPS generate alerts.
- Day 37 → SIEMs collect and correlate those alerts.
- Day 38 → Logs are the raw material underneath everything.

A **log** is simply a record of something that happened:

- A login
- A network connection
- A file being opened
- An error
- A configuration change
- An application event

Everything in security operations is built around logs. A good investigation can use logs to reconstruct an attack step by step. Without the right logs, an investigation can turn into guesswork.

Important logging decisions have to be made **before** an incident:

- What should be logged?
- How long should logs be kept?
- Where should they be stored?
- How can their integrity be protected?

> **You can't investigate what you didn't log.**

### Takeaway

Logs are records of events and the foundation everything in security operations rests on. Alerts, SIEM correlation, and investigations all depend on them.

# The Logs That Matter

The important skill is knowing **which log source can answer a particular investigation question**.

## 1. Authentication Logs

Authentication logs record:

- Who logged in
- When they logged in
- Where they logged in from
- Whether the login succeeded or failed

They are especially useful for investigating brute force, credential stuffing, impossible travel, and account compromise.

## 2. Network Logs

Network logs record:

- What communicated with what
- When communication happened
- Which ports were used
- How much data was transferred

Examples include firewall logs, NAT records, IDS/IPS logs, and network flow records.

They help trace attacker movement, external connections, and possible data exfiltration.

Day 28 showed why NAT logging matters: without the relevant NAT records, it may be difficult to determine which internal device made an external connection.

## 3. System and Event Logs

System logs record what happened on a machine:

- Services starting and stopping
- Configuration changes
- Errors
- Crashes
- Other system events

Windows uses Event Logs, while Linux uses the system journal and logging files.

These logs help identify malware, unauthorised changes, suspicious processes, and endpoint compromise.

## 4. Application Logs

Application logs record what happened inside specific software.

Examples:

- Web server logs
- Database logs
- Email system logs

They can answer questions such as which URLs were requested, which account queried a database, or what a particular service did.

## 5. Audit Logs

Audit logs focus on security-relevant actions such as:

- Who accessed sensitive data
- Who changed permissions
- Who performed administrative actions
- Other privileged activity

They are often important for compliance, insider-threat investigations, and privileged activity investigations.

### Matching Questions to Log Sources

| Question | Useful Log |
|---|---|
| Was an account compromised? | Authentication logs |
| Where did a connection go? | Network logs |
| What happened on a machine? | System/Event logs |
| Which URL was requested? | Application/Web logs |
| Who changed permissions? | Audit logs |
| Where did data leave the network? | Network logs |
| Who accessed sensitive information? | Audit/Application logs |

The important skill is asking:

> **What question am I trying to answer, and which log source contains that information?**

# What Makes a Log Useful?

A useful log needs enough information to answer the questions an investigator may have.

Four important areas are:

1. Accurate timestamps
2. Enough useful detail
3. Appropriate retention
4. Protected integrity

## 1. Timestamps and Synchronised Clocks

Every log entry needs an accurate timestamp, and systems need synchronised clocks.

If one server's clock is twenty minutes wrong, correlating its logs with another system becomes difficult.

This can even affect detections such as impossible travel.

Organisations use **NTP (Network Time Protocol)** to synchronise system clocks.

Accurate time is an essential requirement for correlating logs across systems.

## 2. Enough Detail, But Not Too Much

Useful logs should help answer:

- Who?
- What?
- When?
- Where?
- What was the outcome?

For example:

```text
Login occurred
```

is not very useful.

A record containing the user, source address, time, and success/failure result is much more useful.

There is also a balance. Logging absolutely everything creates huge volumes of data, higher storage/SIEM costs, and more noise.

Good logging is deliberate.

## 3. Retention

Logs need to be kept long enough to investigate realistic incidents.

If an attack is discovered after three months but logs were kept for only two weeks, much of the evidence may already be gone.

Retention balances:

- Investigation requirements
- Storage
- Cost
- Regulatory requirements

Some regulations also require minimum retention periods.

## 4. Integrity

An attacker who compromises a system may be able to delete or alter its local logs.

A defence is to ship logs away from the system as they are generated:

```text
Compromised Host
       ↓
     Logs
       ↓
Central SIEM / Storage
       ↓
Protected Evidence
```

Centralised logging therefore provides both **correlation** and **integrity** benefits.

### Takeaway

A useful logging system needs:

- Accurate and synchronised timestamps
- Enough useful information
- Appropriate retention
- Protected central storage

# Reading a Log Entry

Most logs are readable records of individual events.

A web server entry may contain:

```text
Source IP
Time
Requested resource
HTTP method
Response code
```

In plain language:

> This address, at this time, requested this resource and received this response.

A failed authentication event can similarly contain:

```text
User
Source address
Time
Success / Failure
```

Once the format is understood, reading logs becomes much easier.

---

# Understanding Web Status Codes

HTTP response codes can provide useful clues during investigations.

## 404 — Not Found

Many `404` responses from one address while requesting many different paths can indicate reconnaissance.

Example:

```text
GET /admin       → 404
GET /backup      → 404
GET /login-old   → 404
GET /config      → 404
GET /test        → 404
```

## 401 — Unauthorised

A `401` response indicates that authentication is required or the authentication attempt was not accepted.

A burst of `401` responses can indicate repeated attempts to access protected resources.

## 403 — Forbidden

A `403` response indicates that access to the requested resource is forbidden.

Repeated `403` responses can be useful when investigating attempts to access protected resources.

## 500 — Server Error

A `500` response indicates a server-side error.

It could be a normal application bug, configuration problem, or an attack that triggered a fault. The status code alone does not prove malicious activity.

# The Log Investigation Workflow

The same investigation process used with network traffic also works with logs:

```text
Orient
  ↓
Question
  ↓
Filter
  ↓
Read
  ↓
Conclude
```

## 1. Orient

Understand the log as a whole:

- How many entries?
- What time period?
- What types of events?
- Are there obvious patterns?

## 2. Form a Question

Don't read thousands of lines randomly.

Ask something specific:

> Why are there hundreds of 404 requests from one address?

## 3. Filter

Narrow the log to relevant information.

For example:

```text
Source IP = suspicious address
Status = 404
```

## 4. Read

Look at:

- Timing
- Requested resources
- Source addresses
- Status codes
- User accounts
- Repeated patterns

## 5. Conclude

Decide what the evidence supports.

The underlying skill is similar to packet investigation.

Large log files can contain thousands or millions of entries.

- Search for specific text
- Filter events
- Find an IP address

- Extract useful information
- Examine patterns

Being comfortable with command-line tools makes it easier to work with large amounts of log data.

# Logging in the Real World

Breach investigations repeatedly show how important logging is.

Organisations that contain incidents quickly often have good logging and monitoring.

Major breaches can involve:

- Critical systems that weren't logging
- Logs that weren't retained long enough
- Logs that nobody was reviewing
- Logs that attackers could delete

Logging needs to be planned **before** an incident because historical logs cannot be created after the event.

---

# Logging and Compliance

Logging is also a legal and regulatory concern.

Examples discussed today:

- **PCI DSS** — payment card security
- **HIPAA** — health data in the United States
- **GDPR** — personal data protection in Europe

Organisations may need to demonstrate that required events are being logged and retained.

This is one reason audit logging is particularly important.
