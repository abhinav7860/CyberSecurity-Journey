## Overview

Until now, most of the Linux work I learned was done on the machine in front of me. In real-world system administration and cybersecurity, the systems I work on are often remote servers in data centres, cloud environments, or other locations.

SSH provides a secure command-line connection to those machines.

```text
My Computer

     v

     |

```

SSH is therefore one of the fundamental tools for Linux administration, SOC work, and incident response.

## 1. What SSH Is

SSH stands for **Secure Shell**. It provides a secure shell or command line on a remote machine.

```text
Local keyboard
      |
      v
SSH connection
      |
      v
Remote machine
      |
      v
Command executes there
      |
      v
Result returns to me
```

The commands are executed on the **remote machine**, not on my local computer. This means the Linux skills from this phase can also be used remotely: navigating files, reading files, investigating processes, inspecting network connections, reading logs, running scripts, managing software, and investigating suspicious activity.

## 2. Why SSH Is Important in Cybersecurity

In real security work, systems are often not physically accessible. A SOC analyst may investigate a server, an administrator may maintain cloud machines, and an incident responder may examine a compromised host remotely.

SSH is both an essential administration tool and a critical security doorway.

## 3. SSH Client and Server

SSH uses a **client-server model**.

```text
SSH Client
(My machine)
      |
      | Secure connection
      v
SSH Server
(Remote machine)
      |
      v
Remote shell
```

The remote machine runs an SSH server. The default SSH port is **22**. After authentication, I receive a shell on the remote machine.

## 4. Basic SSH Command

The common syntax is:

```bash
ssh username@address
```

For example:

```bash
ssh user@192.168.1.10
```

When finished, I can leave the remote shell with:

```bash
exit
```

or:

```bash
logout
```

The normal workflow is:

```text
SSH in -> Do the work -> Exit -> Return to local machine
```

## 5. Why SSH Is Secure

SSH encrypts communication between the client and server. If someone intercepts the traffic, they should not be able to directly read the commands, responses, or authentication information.

This is why SSH replaced older remote-access methods that transmitted information in plaintext.

## 6. Secure File Transfer

A related tool is **scp (secure copy)**, which transfers files over the SSH connection. During an investigation, evidence could be securely copied from a remote system for examination, or an administrator could send a script to a remote system.

## 7. SSH Authentication

SSH needs to verify who is connecting. Today's lesson introduced two main methods:

1. Password authentication
2. SSH key authentication

## 8. Password Authentication

The simple method is a password. Passwords can be guessed, brute-forced, stolen, or reused. Internet-facing SSH servers can receive continuous automated login attempts.

This connects directly with the authentication logs from **Day 59**, where repeated failed logins can indicate automated SSH password-guessing activity.

## 9. SSH Keys

SSH key authentication uses a pair:

```text
Private Key + Public Key
```

The private key stays on my machine. The public key is placed on the server. The two are mathematically linked, and the server can verify that I possess the matching private key without the private key leaving my machine.

```text
Private key
     |
     | KEEP SECRET
     v
My machine

Public key
     |
     v
Remote server
```

Key-based authentication is stronger than relying only on a typical password, especially for internet-facing systems. It also previews the asymmetric cryptography I will study later.

## 10. Protecting the Private Key

The private SSH key is one of the most sensitive files I own. It must be tightly protected. This connects to the permissions learned on **Day 51**, especially the `chmod 600` pattern.

```bash
chmod 600 private_key
```

Conceptually:

```text
Owner -> Read + Write
Others -> No access
```

SSH may refuse to use a private key if its permissions are too loose. This shows how file permissions and authentication security work together.

# 11. Day 63 Practical Lab

Today's lab was performed locally rather than connecting to a real remote server. The goal was to check SSH, generate an SSH key pair, inspect the files and permissions, and reason about SSH authentication and security.

## Step 1 — Check Whether SSH Is Installed

Run:

```bash
ssh
```

Running SSH without additional arguments should display usage information, confirming that the SSH client is available.

## Step 2 — Generate an SSH Key Pair

Run:

```bash
ssh-keygen -t ed25519
```

Ed25519 is a modern key type. If it complains, the lesson notes that plain `ssh-keygen` can also be used.

Press **Enter** for the default save location. A passphrase may also be set; for this practice key, pressing Enter for none is acceptable according to the lesson.

The keys are stored in the hidden directory:

```text
~/.ssh
```

## Step 3 — Look at the Keys and Permissions

Run:

```bash
ls -l ~/.ssh
```

The file without `.pub` is the private key. The file ending in `.pub` is the public key.

For an Ed25519 key pair, the common filenames are:

```text
id_ed25519
id_ed25519.pub
```

The private key should be owner-only, following the `chmod 600` pattern.

To view the public key:

```bash
cat ~/.ssh/id_ed25519.pub
```

The exact filename may differ depending on what was created.

## Step 4 — Understand the Connection

No real remote server was required for today's lab. Instead, I reasoned through what would happen if the public key were placed on a remote server and I ran:

```bash
ssh username@that-server
```

The simplified process is:

```text
My machine
   |
   | Private key stays here
   v
SSH connection
   |
   v
Remote server
   |
   | Public key stored here
   v
Authentication challenge
   |
   v
Server verifies matching private key
   |
   v
Authentication succeeds
```

The important security property is that the private key does not need to travel to the remote server.

## 12. SSH as an Attacker Target

SSH is an important security target because successful SSH access can provide command-line access to a server. Internet-facing SSH services can receive automated login attempts trying common usernames and passwords.

```text
Internet
   v
SSH server
   v
Automated login attempts
   v
Username/password combinations
   v
Possible compromise if credentials are weak
```

This activity can generate many failed authentication events and connects directly to the authentication logs discussed on Day 59.

## 13. SSH Hardening

The lesson introduced several ways to improve SSH security:

### Use SSH keys

Key-based authentication is stronger than relying on passwords alone.

### Disable direct root login

Direct root SSH access increases the impact of a successful authentication attempt. Using a normal account first and escalating privileges when required adds another security boundary.

### Limit who can connect

Only appropriate users should be allowed to access SSH.

### Monitor authentication logs

Authentication logs can reveal repeated failed attempts and successful logins.

### Changing the default port

Changing port 22 can reduce automated background noise, but it is **not real security by itself**. Strong authentication, access control, least privilege, and monitoring are more important.

## 14. SSH Security as a Hardening Example

SSH demonstrates a larger defensive-security principle:

```text
Necessary service
      v
Identify risks
      v
Harden it
      v
Monitor it
```

A necessary service does not always need to be removed. Instead, its risks should be reduced through strong authentication, least privilege, restricted access, and monitoring.

## 17. Reasoning Questions

### Q1. Why are SSH keys more secure than passwords?

SSH keys are generally stronger because there is no normal password to repeatedly guess. The private key remains on my machine while the public key is placed on the server. The server verifies that I possess the matching private key without the private key being sent across the network.

### Q2. How are the failed logins from Day 59 connected to SSH?

Internet-facing SSH servers can receive continuous automated login attempts. Attackers' programs may try common usernames and passwords in an attempt to gain access. Therefore, repeated failed authentication entries can be evidence of automated SSH password-guessing activity.

### Q3. Why must the private key have strict permissions?

The private key is a sensitive authentication credential. If another user can read it, they may be able to obtain the credential used to authenticate to systems where the key is trusted. Therefore, SSH expects private keys to have strict owner-only permissions and may refuse to use keys with unsafe permissions.
