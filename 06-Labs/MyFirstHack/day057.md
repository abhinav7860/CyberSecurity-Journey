## Overview

Yesterday I investigated a suspicious file sitting on disk. Today I moved from **files at rest** to **programs that are actively running**.

A running program is called a **process**.

A computer can have dozens or hundreds of processes running at the same time. Most are normal system services, applications, and background tasks. However, if a system is compromised, malware may also be running as a process.

This makes one question especially important during security investigations:

> **What's running on this system?**

A file investigation asks:

> **What could this file do?**

A process investigation asks:

> **What is actually happening right now?**

This is the live-system equivalent of yesterday's suspicious-file investigation.

---

# 1. What Is a Process?

A **process is a running program**.

When a program is launched, the operating system loads it and starts it as a process.

Every process has several important properties.

### Process ID — PID

Every process has a **Process ID (PID)**, a unique number used to identify a specific running process.

### Process Owner

Every process runs as a particular user. A process running as `root` has root's privileges, so an unknown malicious process running as root is much more concerning than one running as an ordinary user.

### Resource Usage

Processes consume CPU and memory. Unexpectedly high resource usage can be a clue. Cryptomining malware, for example, may quietly consume CPU while mining cryptocurrency for an attacker.

### Parent Process

Every process has a **parent** — the process that started it. This creates a process family tree and can help reveal how something came to be running.

```text
Parent Process
      │
      ├── Child Process
      └── Child Process
```

---

# 2. Processes and `/proc`

One of the Linux concepts from Day 48 connects directly to processes:

> **Nearly everything in Linux is a file.**

Running processes are represented under:

```text
/proc
```

Each process has a directory named after its PID. For example:

```text
/proc/1
```

contains files describing the process with PID `1`.

These files can contain information about the program, what it is doing, files it has open, and what it is connected to.

```text
Running Process
      ↓
    /proc/PID
      ↓
Files describing the process
```

This means the file-reading skills I learned earlier can also be used to inspect live processes.

# 3. Process States

Processes can have different states, including:

- Running
- Sleeping
- Stopped

For today's investigation, the essential mental model is:

```text
Process =
Running program
+
PID
+
Owner
+
Resource usage
+
Parent
```

Each property can provide a clue during an investigation.

# 4. Seeing What's Running with `ps`

The `ps` command provides a **snapshot** of running processes.

The commonly used form is:

```bash
ps aux
```

It lists processes with useful information such as:

- Owner
- PID
- CPU usage
- Memory usage
- Command being run

Each line represents one process.

Think of `ps aux` as:

> **A photograph of the system's current activity.**

For security investigation, I can scan the output and look for processes that do not belong.

---

# 5. `top` — Live Process Activity

Unlike `ps`, which gives a snapshot, `top` provides a **live view**.

Run:

```bash
top
```

It continuously updates the process list, usually showing the most resource-hungry processes near the top.

```text
ps  = photograph
top = live video
```

`top` is useful when I want to know:

> **What's happening right now?**

It is especially useful when the system is slow or behaving strangely.

Press:

```text
q
```

to quit `top`.

---

# 6. `htop`

`htop` provides the same general idea as `top`, but with a friendlier interface, easier navigation, colour, and a clearer layout.

If installed:

```bash
htop
```

If it is not installed, `top` works fine.

---

# 7. `ps` vs `top` vs `htop`

| Tool | Type | Best Use |
|---|---|---|
| `ps aux` | Snapshot | Examine the complete process list |
| `top` | Live view | Watch current resource usage |
| `htop` | Live view | Friendlier interactive process monitoring |

A practical workflow is:

```text
top
 ↓
Spot something interesting
 ↓
ps aux
 ↓
Examine the full picture
```

# 8. Spotting a Suspicious Process

The security skill is not simply knowing how to list processes. It is being able to notice:

> **Which process shouldn't be there?**

This requires knowing what normal activity looks like. This is the same **baseline thinking** used in the Networks phase, now applied to processes.

### Suspicious Sign 1: High CPU or Memory Usage

A process using a surprising amount of CPU or memory without an obvious reason deserves investigation. Cryptomining malware is one example.

### Suspicious Sign 2: Unknown Process Running as Root

An unrecognised process running as `root` is concerning because it has root's power.

### Suspicious Sign 3: Strange or Misspelled Name

Attackers may use strange, random-looking, or slightly misspelled legitimate names to hide in plain sight.

### Suspicious Sign 4: Unusual Location

A process executing from an unusual location can be suspicious. The lesson specifically highlights `/tmp` as an attacker-favoured directory from Day 48.

### Suspicious Sign 5: Unexplained Network Connections

A suspicious process making network connections that cannot be explained may be malware communicating externally. This connects to the next lesson.

**Important:** None of these signs automatically proves that a process is malicious. Each is a clue that should lead to further investigation.

---

# 9. Investigating a Suspicious Process

The investigation method is similar to yesterday's file investigation.

### Step 1 — List the processes

```bash
ps aux
```

### Step 2 — Look for unusual behaviour

Check for:

- Unexpected resource usage
- Unknown owners
- Root-owned suspicious processes
- Strange names
- Unusual locations
- Unexplained network activity

### Step 3 — Investigate what caught your attention

Ask:

- What is this process?
- Who owns it?
- What is it doing?
- Where did it come from?
- What started it?

The `/proc` directory can also be used to learn more about the process.

```text
ps aux
   ↓
Spot something unusual
   ↓
Investigate process
   ↓
/proc/PID
   ↓
Understand its activity
```

# 10. Stopping a Process with `kill`

Once a process that should not be running has been identified, it can be stopped using:

```bash
kill PID
```

For example:

```bash
kill 1234
```

The `kill` command tells that process to terminate.

In incident response, stopping an identified malicious process can halt its current activity. The associated file should still be preserved as evidence for analysis, following yesterday's suspicious-file investigation.

```text
Identify malicious process
          ↓
       kill PID
          ↓
Process stops
          ↓
Preserve file as evidence
```

# 11. File Investigation vs Process Investigation

| Investigation | Main Question |
|---|---|
| File investigation | What could this file do? |
| Process investigation | What is actually happening right now? |

A suspicious file may only be a potential threat while sitting on disk. Once it is running, it becomes a process and may actively consume resources, make network connections, and perform actions on the system.

Both static and live investigation are important.

---

# 12. Processes as Live Evidence

A compromised system may contain malicious activity that is more visible in its running state than on disk.

Some malware can leave little trace on disk while actively operating in memory. This is why incident responders may need to capture and examine the running state of a system.

Processes are evidence too.

```text
System running
      ↓
Processes active
      ↓
Live evidence
      ↓
May disappear when system is shut down
```

This makes the question:

> **What's running?**

an important early question during live-system investigation.

# 13. Processes Connect to Network and Logs

A suspicious process usually does not operate in isolation.

```text
Process
```

# 14. Practical Exercise

Today's exercise focuses mainly on read-only observation, followed by one safe process stop using a process I started myself.

## Step 1 — Take a Snapshot with `ps`

Run:

```bash
ps aux
```

Look at a few lines and identify the owner, PID, CPU usage, memory usage, and command. Notice which processes are owned by `root` and which belong to your own user.

## Step 2 — Watch the Live View with `top`

Run:

```bash
top
```

Watch the process list for a moment and notice CPU and memory usage changing. If `htop` is installed, it can also be tried:

```bash
htop
```

Press `q` to leave `top`.

## Step 3 — Look at a Process as a File

Run:

```bash
ls /proc
```

You should see many numbered directories. These numbers correspond to process IDs.

Choose a PID you saw earlier and inspect its directory. For example:

```bash
ls /proc/1
```

This demonstrates the Linux principle that processes can be inspected through files under `/proc`.

## Step 4 — Start a Safe Process

Start a harmless process yourself:

```bash
sleep 300 &
```

The `&` places the process in the background so the terminal remains available. The system prints a number — this is the PID.

## Step 5 — Find the Process

Run:

```bash
ps aux
```

Look for `sleep` in the command column and identify its PID.

## Step 6 — Stop the Process

Use:

```bash
kill PID
```

Replace `PID` with the actual PID of the `sleep` process.

For example:

```bash
kill 1234
```

The harmless process is terminated. This demonstrates identifying a specific process by PID and stopping it.

# 15. Command Reference

| Command | Purpose |
|---|---|
| `ps aux` | Take a snapshot of running processes |
| `top` | View processes and resource usage live |
| `htop` | Friendlier live process viewer |
| `ls /proc` | View process directories and other `/proc` entries |
| `ls /proc/PID` | Inspect files describing a specific process |
| `sleep 300 &` | Start a harmless background process |
| `kill PID` | Stop a process using its PID |
| `q` | Quit `top` |
