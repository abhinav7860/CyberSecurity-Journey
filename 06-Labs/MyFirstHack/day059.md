# 2. Important Logs in `/var/log`

The exact log files vary between Linux systems, but several important
categories are common.

## Authentication Log

The authentication log is one of the most security-relevant logs.

It is usually called:

``` text
auth.log
```

on Debian and Ubuntu systems, or:

``` text
secure
```

on other systems.

It records events such as:

-   Logins
-   Logouts
-   Failed login attempts
-   `sudo` usage
-   Other security-significant access events

The `sudo` audit trail from Day 52 can therefore appear here.

A pattern such as:

``` text
Failed login
Failed login
Failed login
Successful login
```

can be an important sign during an investigation.

## System Log

The general system log is commonly called:

``` text
syslog
```

on Debian/Ubuntu systems, or:

``` text
messages
```

on others.

It contains general system activity, including:

-   Services starting
-   Services stopping
-   Hardware events
-   Other system and software activity

It is usually noisier than the authentication log, but it can contain
important evidence.

## Application and Service Logs

Individual applications and services can maintain their own logs.

For example, a web server may record requests it receives.

These logs are useful when investigating a particular service.

``` text
Application
     ↓
Its log
     ↓
Activity specific to that application
```

# 3. The Linux Journal and `journalctl`

Many modern Linux systems also use a system component called the
**journal**.

The command used to query it is:

``` bash
journalctl
```

The journal stores logs in a structured way, and `journalctl` can filter
them by:

-   Time
-   Service
-   Priority
-   Boot

A Linux system may use plain-text files in `/var/log`, the journal, or
both.

The investigative idea is the same:

``` text
System activity
      ↓
Recorded in logs
      ↓
Read and filter the records
      ↓
Understand what happened
```

# 4. Reading Logs with `tail`

Logs generally grow at the bottom, so:

``` bash
tail
```

shows the most recent entries.

This answers:

> **What just happened?**

``` text
Log file
   ↓
tail
   ↓
Recent activity
```

`tail` can also be used in follow mode to watch new entries as they
arrive.

This can be useful for watching authentication activity in real time.

------------------------------------------------------------------------

# 5. Reading Logs with `less`

Logs can become very large.

I can use:

``` bash
less
```

to move through a long log and search within it.

``` text
Large log
   ↓
less
   ↓
Read and search through it
```

This is useful when I want to examine a section of a log instead of only
viewing its latest entries.

------------------------------------------------------------------------

# 6. Searching Logs with `grep`

`grep` is one of the most important tools when investigating logs.

A large log can contain thousands of lines, while I may only need a
small part of it.

For example, searching an authentication log for:

``` text
failed
```

can reveal failed login attempts.

Searching for a username can help trace that account's activity.

Searching for a date or time can focus the investigation on a particular
period.

``` text
Large log
   ↓
grep
   ↓
Relevant entries
```

# 7. Pipelines and Log Analysis

The pipelines from Day 55 are especially useful for logs.

A raw log can contain an overwhelming amount of information.

Pipelines can help answer questions such as:

-   How many failed login attempts occurred?
-   Which addresses attempted to log in?
-   Which source attempted most often?
-   How frequently did attempts occur?

The general idea is:

``` text
Search
  ↓
Sort
  ↓
Remove duplicates / count
  ↓
Useful finding
```

This uses the composing mindset from Day 55:

> Break a larger question into a sequence of smaller operations.

Instead of asking:

> "What single command analyses this entire log?"

I ask:

> "What sequence of simple steps will give me the answer?"

This can turn a huge log into a small set of useful investigative facts.

# 8. Finding the Story in Logs

Logs can help reconstruct what happened during an incident.

This connects directly to the forensic timeline from Day 39.

The investigator's question is:

> **What happened here, and in what order?**

For example, a password-guessing attack may appear as:

``` text
Failed login
Failed login
Failed login
Failed login
Successful login
```

The failed attempts can indicate password guessing, while the successful
login may represent the point where access was obtained.

After gaining access, an attacker may create an account for persistence.
Account creation can be recorded in logs.

An attacker may also use `sudo` for elevated privileges, leaving an
audit trail in the authentication log.

Starting or stopping services can also leave records in system logs.

The individual traces become a story when placed in order.

------------------------------------------------------------------------

# 9. Timestamps and the Forensic Timeline

Timestamps are extremely important when reading logs.

They allow events to be placed in order:

``` text
10:01  Failed login
10:02  Failed login
10:03  Successful login
10:05  Account created
10:07  Privileged action
```

This creates a sequence of events.

``` text
Individual log entries
        ↓
Order by time
        ↓
Sequence of events
        ↓
Forensic timeline
```

This is the same principle behind the forensic timeline from Day 39.

A useful live-system investigation can now follow this pattern:

``` text
1. Look at processes
        ↓
   What's running?

2. Look at network activity
        ↓
   What is it talking to?

3. Look at logs
        ↓
   What has happened?

4. Connect the evidence
        ↓

```

This is similar to what a SIEM does by correlating information from
different sources, except here I am learning to connect the evidence
manually on one Linux system.

# 12. Investigation Questions

When investigating logs, I should start with specific questions.

### When did this account last log in?

Search the authentication log for that account.

### Were there failed login attempts before a successful login?

Search for failed authentication attempts and examine what happened
afterward.

### What happened around the suspected breach time?

Focus on the relevant time window.

### Was `sudo` used, and by whom?

Check the authentication log for the relevant audit events.

The important skill is:

``` text
Question
   ↓
Choose the right log
   ↓
Choose the right tool
   ↓
Extract evidence
   ↓
Build the timeline
```

# 13. Why Logs Matter in Security

Processes and network connections mainly show the present.

Logs preserve information about the past.

``` text
Processes
↓
Present activity

Network
↓
Present communication

Logs
↓
Historical activity
```

This makes logs especially useful when reconstructing an incident.

For example:

``` text
Failed login attempts
        ↓
Successful login
        ↓
Account creation
        ↓
Privilege escalation
        ↓
Other activity
```

The logs can help turn separate events into a narrative.
