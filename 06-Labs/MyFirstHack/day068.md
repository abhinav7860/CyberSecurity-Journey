## 2. What Is Encryption?

Encryption is the process of converting readable information into an unreadable form so that unauthorised people cannot understand it.

The basic idea is:

```text
Plaintext
   |
   | Encryption + Key
   v
Ciphertext
   |
   | Decryption + Key
   v
Plaintext
```

### Plaintext

**Plaintext** is the original readable information.

Example:

```text
My password is secure
```

### Ciphertext

**Ciphertext** is the scrambled, unreadable version of the information after encryption.

An attacker may be able to see the ciphertext, but without the required key, it should not be possible to recover the original information.

### Encryption

Encryption converts:

```text
Plaintext → Ciphertext
```

### Decryption

Decryption converts:

```text
Ciphertext → Plaintext
```

### Key

A **key** is the secret piece of information that controls how the data is scrambled and how it can be unscrambled.

The key is one of the most important parts of the whole encryption process.

## 3. My Mental Model — A Locked Box

The easiest way for me to understand encryption is to imagine a locked box.

```text
          Plaintext
              |
              v
       +---------------+
       |  Locked Box   |
       |   + Key       |
       +---------------+
              |
              v
        Ciphertext
              |
        Hostile Network
              |
              v
       Person with Key
              |
              v
          Plaintext
```

The readable information is placed inside the box and the box is locked.

The locked box can then travel across a network where other people may be able to see it.

However, only someone with the correct key should be able to open it and read the information.

This helped me understand that encryption does not necessarily stop an attacker from **seeing that data is being transmitted**. Its purpose is to prevent the attacker from understanding the protected information.

## 4. Security Depends on the Key, Not on Hiding the Method

One important concept I learned is that the security of modern encryption should depend on the **key**, not on keeping the encryption method secret.

Modern encryption algorithms are generally designed with the assumption that attackers may know which algorithm is being used.

For example:

```text
Attacker knows:
- The encryption method
- The ciphertext
- How the system works

Attacker does not have:
- The secret key
```

Without the key, properly implemented modern encryption should still protect the information.

This is important because a security system that depends on keeping the method itself secret is much weaker.

### Main idea

> The secret should be the key, not the encryption method.

## 5. What Does Encryption Protect?

The primary security property provided by encryption is **Confidentiality**.

From the CIA Triad:

```text
CIA Triad
│
├── Confidentiality
│      └── Encryption is a major protection
│
├── Integrity
│      └── Encryption can contribute, but is not usually enough alone
│
└── Availability
       └── Encryption does not guarantee availability
```

### Confidentiality

Encryption prevents unauthorised people from reading protected information.

### Integrity

Encryption can contribute to protecting integrity, but encryption by itself should not be treated as a complete integrity mechanism.

Other mechanisms are normally needed as well. I will study **hashing** later, including on Day 70.

### Availability

Encryption does not guarantee that information or a service will remain available.

In fact, encryption can also be misused to affect availability, which I learned through the example of ransomware.

## 6. Encryption in Transit

**Encryption in transit** protects information while it is moving from one place to another.

Examples include:

- Website traffic
- SSH connections
- Secure messages
- HTTPS connections
- Other network communications

A simplified view is:

```text
Computer A
    |
    | Encrypted Data
    v
Untrusted Network
    |
    | Encrypted Data
    v
Computer B
```

Someone monitoring the network may be able to capture the traffic, but the encrypted content should not be readable without the required key.

This connects directly with what I studied earlier about **eavesdropping** and network traffic.

## 8. Encryption at Rest

Encryption is not only useful when data is moving.

It can also protect data while it is **stored**.

This is called **encryption at rest**.

Examples include:

- Files
- Hard drives
- Databases
- Backups
- Phone storage
- Laptop storage

A simplified example:

```text
Stored Data
    |
    v
Encrypted Storage
    |
    v
Protected if Storage Is Stolen
```

One common recommendation is to use **full-disk encryption** so that stored information is protected if the physical device is lost or stolen.

A properly protected system may need **both**.

              Secure System

## 10. The Biggest Practical Problem — Key Management

One of the most important things I learned today is that using encryption is not just about choosing an algorithm.

The difficult practical problem is often **key management**.

A system needs to securely handle keys throughout their lifecycle.

This includes:

- Generating keys
- Distributing keys
- Storing keys
- Protecting keys
- Rotating keys
- Revoking keys
- Retiring keys

### Why is key sharing difficult?

Imagine two people who want to communicate securely.

They need a key.

But if they send the secret key over the same untrusted network they are trying to protect, an attacker could potentially intercept it.

```text
Person A
   |
   | "Here is the secret key"
   v
Untrusted Network
   |
   +------> Attacker captures key
   |
   v
Person B
```

Now the attacker has the key that is supposed to protect the communication.

This creates an important problem:

> How can two parties securely share a secret key over an untrusted network?

This leads directly into the next topic: **symmetric vs asymmetric encryption**.

## 11. Encryption Does Not Protect Everything

Encryption is powerful, but it is not a magic solution.

There are important limitations.

### 11.1 It Does Not Automatically Protect Endpoints

If an endpoint is compromised, the attacker may be able to access information **after it has been decrypted**.

```text
Encrypted Data
      |
      v
Compromised Computer
      |
      v
Decrypted Data
      |
      v
Attacker
```

Encryption protects the data while it is encrypted, but it cannot solve every problem on a compromised endpoint.

### 11.2 Stolen or Leaked Keys Break the Protection

If an attacker obtains the required key, encryption may no longer protect the data from that attacker.

This is why protecting keys is extremely important.

```text
Strong Encryption
       +
Poor Key Protection
       =
Weak Security
```

### 11.3 Encryption Alone Is Not Enough

A system can have an encrypted connection and still be vulnerable.

For example:

```text
User
  |
  | Encrypted Connection
  v
Vulnerable Server
  |
  v
Security Problem
```

The communication may be encrypted, but the server itself could still contain vulnerabilities.

This connects with what I learned on Day 67:

**A security control should be considered in the context of the overall threat, vulnerability, and risk.**

## 12. Encryption Can Also Be Misused

Encryption is normally used as a defensive security control, but attackers can also use encryption maliciously.

A major example is **ransomware**.

The attacker can encrypt a victim's data and withhold the key.

```text
Victim's Data
      |
      v
Attacker Encrypts Data
      |
      v
Encrypted / Unavailable Data
      |
      v
Key Withheld by Attacker
```

The problem here is related to **Availability**.

The data may still exist, but the victim cannot access it.

This reminded me that a security technology itself is not automatically good or bad. What matters is **how it is used and what security problem it is addressing**.
