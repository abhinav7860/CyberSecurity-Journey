## What Exactly Is Zero Trust?

Zero trust starts from one uncomfortable observation:

> **Trust is the vulnerability.**

Many attacks work because systems or users are trusted by default.

Examples from earlier lessons:

- **ARP poisoning** works because devices trust whoever answers.
- **DNS spoofing** works because resolvers trust the response.
- **Man-in-the-middle attacks** work because parties trust that their connection is direct.
- **Lateral movement** works because traditional networks often trust devices once they are inside the network.

The traditional model assumes that the inside of a network is trustworthy. If an attacker gets inside through phishing or another method, they can potentially move through the network.

Zero trust changes this approach.

The main principle is:

> **Never trust, always verify.**

No user, device, or connection is trusted simply because of its location.

Every access request must be verified.

### Takeaway

Zero trust treats trust itself as a security risk. Being inside a network does not automatically make a user or device trustworthy.

The core idea is:

> **Never trust, always verify.**

# The Old Model: Castle and Moat

The traditional network security model is often described as the **castle-and-moat model**.

The network had a strong perimeter:

```text
                INTERNET
                    |
             [ Firewall ]
                    |
             ┌─────────────┐
             │   INTERNAL  │
             │   NETWORK   │
             │             │
             │  TRUSTED    │
             └─────────────┘
```

The goal was to keep attackers outside.

Once someone got inside, however, they were generally trusted.

This created a:

> **Hard shell, soft centre**

model.

Inside the network:

- Devices could communicate more freely.
- Users did not always need to re-prove themselves.
- Internal systems were treated as trusted.

This model made more sense when:

- Employees worked inside offices.
- Company computers were physically inside the organisation.
- Data was stored inside the corporate network.
- The network perimeter was a meaningful boundary.

## Why the Castle-and-Moat Model Broke

### Cloud

Company resources moved outside the traditional corporate perimeter.

### Remote Work

Employees can work from homes, cafes, airports, and other locations outside the office.

### Mobile Devices

More devices connect from different locations and networks.

### Phishing

Attackers can gain access to the internal environment by compromising a single employee account or device.

Once inside, the trusting interior becomes a target for lateral movement.

The problem is:

> **Being inside the network no longer means being trustworthy.**

### Takeaway

The old castle-and-moat model relied on location to determine trust. Cloud, remote work, mobile devices, and phishing weakened that assumption. Zero trust recognises that the perimeter is no longer enough.

# Principles of Zero Trust

Zero trust is not a single product.

It is an **architectural philosophy** built around several principles.

## 1. Verify Explicitly, Every Time

Every access request should be authenticated and authorised using available information:

- Who the user is
- What device they are using
- Where they are connecting from
- What resource they are requesting
- Whether the request appears anomalous

Instead of:

```text
You're inside → Access granted
```

the model becomes:

```text
Request
   ↓
Verify identity
   ↓
Verify device/context
   ↓
Authorise access
   ↓
Allow or deny
```

Strong authentication, especially **multi-factor authentication (MFA)**, is an important part of this principle.

## 2. Use Least Privilege

Least privilege was introduced earlier with network segmentation.

Users and devices should receive:

> **Only the access they genuinely need, and no more.**

If an account becomes compromised, its access is limited.

```text
Compromised Account
        ↓
Limited Permissions
        ↓
Limited Access
        ↓
Limited Damage
```

## 3. Assume Breach

Instead of assuming the network is clean, zero trust assumes:

> **An attacker may already be inside.**

Because of this, the network is designed to limit what an attacker can do.

That means:

- Strong verification
- Heavy segmentation
- Continuous monitoring
- Limited privileges

## 4. Microsegmentation

Microsegmentation is segmentation taken much further.

Traditional segmentation might create a few large zones:

```text
Marketing
Finance
Servers
Guest
```

Microsegmentation creates much smaller security boundaries, potentially down to individual workloads.

Every connection between systems can have its own controls.

The goal is to prevent attackers from freely moving around inside a trusted zone.

## 5. Continuous Monitoring

Trust is not permanent.

Even after a request has been verified, the system continues monitoring activity.

If behaviour changes, access may be revoked.

This connects directly to previous lessons:

- IDS
- SIEM
- Logs
- Network forensics

### Takeaway

The major zero-trust principles are:

1. **Verify explicitly**
2. **Use least privilege**
3. **Assume breach**
4. **Use microsegmentation**
5. **Continuously monitor**

# Zero Trust in Practice

## Zero Trust Is a Journey

An organisation cannot normally switch from a traditional network to zero trust overnight.

Existing environments contain old systems, legacy applications, and architectures based on the trusted-inside model.

A practical transition is gradual:

1. Identify sensitive resources.
2. Add strong verification.
3. Apply least privilege.
4. Segment critical systems.
5. Expand zero-trust controls over time.

Mature organisations generally describe themselves as being:

> **On a zero-trust journey**

rather than claiming the project is completely finished.

# Identity Becomes the New Perimeter

When location no longer determines trust, **identity** becomes much more important.

Instead of asking:

> "Are you inside the network?"

the system asks:

> "Who are you, and should you have access to this resource?"

This makes the following important:

- Identity and Access Management (IAM)
- Multi-Factor Authentication (MFA)
- Single Sign-On (SSO)
- Strong identity verification

The perimeter effectively moves from the network edge toward the identity of users and devices.

```text
OLD MODEL

Location → Trust


ZERO TRUST

Identity + Device + Context
             ↓
          Decision
             ↓
        Access / Deny
```

# The User Experience Problem

Zero trust has a real usability challenge.

If verification is implemented badly, users may experience:

- Constant authentication prompts
- Unnecessary access blocks
- Frustration
- Workarounds

The goal is to make strong verification as unobtrusive as possible.

A good implementation may verify users in the background and only request additional proof when activity appears risky.

> **Security that people route around isn't security.**

# Zero Trust Frameworks

The lesson mentions:

- **NIST SP 800-207** — a formal zero-trust architecture standard from the US National Institute of Standards and Technology.
- **Google BeyondCorp** — an influential real-world implementation.
- Major technology vendors such as Microsoft and Google offer zero-trust platforms.

The important point is that zero trust is now an established security architecture rather than simply a buzzword.

# Zero Trust for Maya's Shop

Maya does not need to build a complete enterprise zero-trust architecture.

She can apply the basic principles.

### MFA

Use strong authentication with MFA on business accounts.

### Separate Critical Systems

Keep the payment system separated from other devices.

### Least Privilege

If an employee only needs access to certain systems, do not give them access to everything.

### Cloud Providers

Choosing cloud providers that operate strong security architectures can provide additional protection without Maya building everything herself.

The technology may be enterprise-scale, but the principle is universal.

# Important Terms

## Zero Trust
A security architecture based on not trusting users, devices, or connections by default and verifying access requests.

## Never Trust, Always Verify
The central principle of zero trust.

## Castle-and-Moat Model
The traditional security model that strongly protects the perimeter while generally trusting systems and users inside it.

## Least Privilege
Giving users and devices only the access they genuinely need.

## Assume Breach
Designing security with the assumption that an attacker may already be inside.

## Microsegmentation
Dividing environments into very small security zones and controlling connections between them.

## Continuous Monitoring
Continuously observing users, devices, sessions, and activity so access can be changed or revoked when behaviour becomes suspicious.

## Identity as the Perimeter
Using strongly verified identity and context as the basis for access instead of relying mainly on network location.

## MFA
**Multi-Factor Authentication** — an authentication approach using multiple factors to verify identity.

## NIST SP 800-207
The zero-trust architecture standard mentioned in today's lesson.
